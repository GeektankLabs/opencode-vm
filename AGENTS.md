# AGENTS.md

This file provides guidance to ai agents when working with code in this repository.

## Project Overview

**opencode-vm** is a single Bash script (`opencode-vm.sh`) that runs [OpenCode](https://opencode.ai) inside an isolated Lima VM on macOS. It provides a fresh-per-session workflow: a persistent base VM (`oc-base`) is cloned for each session, the user's project directory and OpenCode config are mounted in, and the session VM is deleted on exit.

Key design goals:
- Isolation via Lima VM with controlled network egress (nftables)
- Host project directory mounted read-write so IDE/Git workflow stays on host
- OpenCode config + user state synced via per-project host state and per-session working copy
- Host LLM servers (LM Studio :1234, Ollama :11434) reachable from VM via `host.lima.internal`. Provider configs are managed via `opencode-vm provider {add|new|refresh|rm}`. Since v0.4.12, every `opencode-vm start` auto-runs `provider_refresh_all_quiet` against host-local providers (`localhost`/`127.0.0.1`/`192.168.5.2`/`host.lima.internal`) so newly-loaded LM Studio / Ollama models surface immediately in the next session — disable with `OCVM_PROVIDER_AUTOREFRESH=0`. Capability tagging for newly-discovered models lives in `_provider_cap_heuristics`: tries `/v1/models` JSON metadata first (`capabilities[]`, `modalities.input`, `vision`/`thinking` booleans), falls back to id-pattern matching (`llava|qwen*-vl|pixtral|gemma3|...` for vision; `qwq|deepseek-r1|o1|o3|*-thinking` for reasoning). User-set per-model flags are preserved verbatim — refresh never silently downgrades them.
- **Provider auth synchronization (since v0.5.52):** each controlled runtime records the exact host `auth.json` seeded into it. Controlled finalization performs a provider-level three-way merge against that baseline and the latest host state; unchanged stale copies never win, independent providers combine, and concurrent OAuth changes use host-recorded completion order rather than expiry or mtime. Prepared publication metadata repairs interrupted commits. Login/logout run through OpenCode inside the current project's tracked VM and checkpoint to the session share; deliberate logout publishes a tombstone at finalization, while a later explicit login clears it. Generic history rsync excludes `auth.json`. Auth commits and lifecycle takeover use separate host locks, and destructive cleanup fails closed when capture or ownership validation fails.
- LAN access restricted by default with opt-in allowlists
- **No git credentials inside the VM.** The session VM intentionally has no SSH keys, no SSH-agent forwarding, no HTTPS tokens, and no access to the user's git origin. All `git push`, `git fetch`, and PR operations happen on the host (the IDE workflow that stays outside the VM). This is a hard design boundary: a YOLO-mode AI agent inside the sandbox must not be able to reach the user's origin remote. Do not add credential-forwarding, even as an opt-in — if a workflow seems to require it, the correct answer is to move that workflow to the host. **Note on SSH tooling:** the base VM ships `openssh-client`, `sshpass`, `autossh`, `mosh`, `sshfs`, plus standard network-discovery tools (`nmap`, `arp-scan`, `arping`, `tcptraceroute`, `tshark`, …) so agents can perform legitimate SSH and network operations to **non-origin** targets (lab hosts, LAN devices, Proxmox nodes, customer servers) without per-session installs. Having the binaries available does **not** weaken the boundary — credentials are still never copied or forwarded into the VM. If a target requires authentication, the user provides it explicitly per session (env var, MCP credential prompt, manual paste into `~/.ssh/`) and it is never persisted across sessions.

## Architecture

**Agent-managed work sessions:** actual agentic WORK creation/admission through MCP, A2A or OpenLive is adopted automatically by the backend; reads and pure management stay neutral, and manual sessions stay manual until work adoption. Managed children/reuse follow the same contract. Authorized local development includes normal local Git work and commits without separate confirmation; explicit read-only/review/task restrictions remain binding. Missing business decisions end as ordinary readable `INPUT_REQUIRED` text for an orchestrator follow-up in the same session, without native Questions. Remote publishing remains operator-only: VM/host credential and origin separation is primary, OpenCode no-Ask Denies are defense-in-depth. See `docs/MANAGED-SESSIONS.md`. For candidate-to-release completion, exact-commit verification and preserving a working runtime while the gate is red or unverified, follow [`docs/RELEASING.md`](docs/RELEASING.md).

**ACH-1 consolidated integration (script 0.6.6 / MCP 0.1.20 / skill r23):** Hub follows Profiles → Connections → Logs with stable honest states (`not_configured`, `unverified`, `not_ready`, `ready`), local help, preserved drafts/focus and explicit conflict/uncertain-save readback. Schema 1/2 readers normalize Deep/Standard/Execution/Design/Review; base writes retain schema 1, first optional mapping checks active MCP tool schemas and backs up exact original bytes before atomic schema-2 publication. Design → Standard and Review → Deep → Standard skip only null and stop at configured unavailable/incomplete mappings. Review evaluates without automatic findings implementation. This incorporates the r21 additive task writes and Header/r22 contracts; real Mac/Safari/VoiceOver and external operator acceptance remain separate. See `hub/README.md` and the ACH-1 task concept plan.

**Task writes and Management Journal (adapter 0.1.22):** The optional Board catalog has nineteen tools. `add_task_document_bindings` remains the add-only schema-3 bundle. `add_task_management_note` appends to a lazy, task-specific persistent journal without modifying native Description; `get_task_management_history` provides bounded recent/cursor/after-checkpoint/latest-checkpoint reads and revision-bound legacy Description ranges. The cooperating `flock` serializes adapter writers, not UI/filesystem writers or scheduler runs. Uncertain writes are reconciled by journal readback; corrupt/incomplete data fails closed. Legacy notes remain in Description. Operator authentication is not provided by journal ordering/markers. The skill requires discovered-capability use and preserves no-blind-retry behavior. Task-document readback and separate Board move/status contracts remain unchanged; annotations are hints, not approval guarantees. See `docs/MCP-INTERFACE.md` for the current surface.

**Provider MVP completion (v0.5.53; CLI surface revised in v0.5.57):** controlled lifecycle finalization stops the owned guest runtime and captures auth through the VM transport under a guest runtime lock; stopped recovery requires a verified host-retained snapshot, never an unverified share seed. History rsync excludes auth in both directions. Provider management splits into two host-side classes: **custom endpoints** (`provider custom new|add|sync|rm`; endpoint + API key, model-list sync from `/v1/models`, no session needed) and **subscriptions** (`provider subscription new` prints WebUI steps — OAuth has no CLI flow — and `provider subscription rm <id>` deletes the stored credential host-side and records a logout tombstone). `provider list` groups by credential kind and only reports live runtime availability (`RUNTIME`) when the project's web server is reachable; a running non-web session or an absent server is a benign `unknown` (exit 3 from the VM payload), while a reachable but incompatible server fails closed. The adapter is not pinned to an OpenCode version: OpenCode ships patches continuously, so the live server interface is validated at runtime and an unsupported interface fails closed naming the detected version. When the stored auth format cannot be three-way merged (an entry shape the merge does not recognize, e.g. after an OpenCode update), finalization publishes the newest runtime auth state wholesale and warns that the merge or OpenCode compatibility needs updating; the same warning is emitted at session start if the host file already uses an unrecognized format. Provider configuration removals are recorded in `~/.opencode-vm/removed-providers.json` and respected during merge and old-session publication. A pre-baseline session (started before baseline tracking) cannot be merged automatically: `attach` preserves its candidate and, when session and host differ, asks interactively (session union vs. host) with a secret-free provider comparison, or refuses when non-interactive. No new auth background process is introduced. Real macOS/Lima and provider acceptance remains a separate required check.

The entire tool is one Bash script: `opencode-vm.sh`. Two small JSON registries live beside it: [`skills/registry.json`](skills/registry.json) and [`mcps/registry.json`](mcps/registry.json). The script remains the single source of truth — registries are data that the script reads at runtime, not independent modules.

**Optional web editor (v0.5.69):** `web --editor` adds pinned code-server 4.139.1 inside the project VM, with uploads/downloads, local Git, terminal and a minimal embedded diagnostic extension. `--no-editor` disables it; reconnect retains the choice, fresh sessions opt in again. HTTPS uses the existing certificate at public `P+4` (even with web `--no-tls`); the atomic SSH-forward block expands to five ports and shifts together on collisions. Editor login uses the web password, and explicit `--no-auth` applies to it too. The owned `ocvm-editor` transient systemd service runs under `opencode-sandbox`; finalization stops its entire service control group before persisting `editor/user-data/User` to project state. Editor payloads are embedded in the script for standalone parity. The Output channels read existing logs and bounded stored activity; MCP adapter 0.1.5 adds metadata-only start/end/duration diagnostics for tool calls. A completed call is not agent task completion. Certificate trust for webviews and current acceptance are documented in [`docs/WEB-EDITOR.md`](docs/WEB-EDITOR.md).

**Web editor default (v0.5.71):** Web sessions now enable the editor by default, including attaching to older web sessions whose editor flag was off by default. Only `SESS_EDITOR_DISABLED=1` records an explicit `--no-editor` opt-out; bare reconnect/attach retains that decision, `--editor` clears it, and a fresh web session defaults on again. The effective editor is advertised in the service banner after readiness. Terminal-mode sessions do not start an editor.

**OpenCode web launcher (v0.5.79; Taskboard/default-on in v0.5.90):** The normal project HTML page remains the top-level document. The loopback web proxy conservatively injects same-origin external launcher assets only into bounded UTF-8 OpenCode SPA HTML responses on the active project route or `/new-session`; the root seed still initializes the project and redirects as before. The launcher catalog presents Editor (P+4), Project Management (Taskboard, P+5), then Agent Control (host-local Hub) when their project-bound readiness checks pass. Web start and web reattach enable the launcher by default; `--no-launcher` suppresses it for one invocation without stopping either app. API/assets/uploads/WebSockets and unsafe/unknown HTML response forms are passed through without launcher injection.

**VM Lifecycle:** `oc-base` (provisioned once via `init`) → cloned per session → session deleted on exit.

**Project Taskboard Phase 1 (adapter 0.1.13):** The optional eight project task tools now use a bounded full local scan of the pinned v0.6.0 upstream `/api/tickets` response for case-insensitive title/description matching, session-to-task reverse lookup and optional status/updated-since filters. The backend has no search pagination; exceeding 1 MiB/500 scanned tasks, 50 matches or a 40-KiB task JSON output fails with `TASK_SEARCH_INCOMPLETE` rather than returning partial or false-negative results. UI-created tickets have deterministic public `task_<UUID>` IDs without lazy read-side writes; exact ID lookup and `get_project_task.links` expose existing generic session/message/result/artifact references. Separate message links from one session are retained. The schema-1 sidecar rejects invalid/unknown formats, and writers reload under a process-shared `flock` before atomic publication. Only the configured project-local scope is accepted; no board-to-session status coupling or UI/MCP-wide CAS is introduced. The ChatGPT-side orchestrator skill adds search-before-create and a read-only remainder preview. Greenfield development without new Board auth is a deliberate scope decision; a central HTTPS/auth proxy remains a later project.

**Multi-Project v1 (adapter 0.1.16):** Five more Board Project/transfer tools expose a confirmed normal `Inbox`/`INBOX` default, additional workstreams in the same repository DB and a durable, recoverable default-to-workstream transfer. No read creates a Project. Existing canonical defaults keep their ID/name/prefix. The schema-2 sidecar accepts schema 1 on reads and journals native staging/deletion/remapping/activation; stable public task IDs and sidecar links/comments survive. The marked target can temporarily appear in upstream Done without meaning business completion; uncertain transfers fail closed and require reconciliation by the same request UUID. The ChatGPT skill r12 suggests classification only for persistent outcomes and confirms mutations. The original global/local `transfer_project_task` remains unavailable. See [`docs/MCP-INTERFACE.md`](docs/MCP-INTERFACE.md) for the exact contract and acceptance limitations.

**Incoming MCP connector (since v0.5.60; default-on since v0.5.61):** `opencode-vm web [--mcp-port PORT|--no-mcp]` exposes the current project's existing OpenCode runtime to external MCP clients on a dedicated host-loopback endpoint. Since v0.5.62, terminal `start` also enables MCP when the project has an OpenAI MCP assignment: internal mode `tui-mcp` runs one loopback `opencode serve` backend and attaches the TUI, without web/A2A LAN forwards. New sessions reserve a free port in `40960..41059`; explicit ports fail on collision and reconnect retains its port/token. `--no-mcp` suppresses MCP/tunnel for one invocation only; subsequent normal starts/reconnects re-evaluate the project assignment. This is not the registry-driven `opencode-vm mcps` subsystem: those entries are servers OpenCode consumes, while this adapter is a server outside clients consume. Current adapter 0.1.14 in `adapters/mcp/` uses stateless Streamable HTTP, requires `X-OCVM-MCP-Token` on every `/mcp` and `/healthz` request, and exposes eighteen core tools, including `upload_attachment`, asynchronous `send_message`, guard-bound `supersede_unresolved_submission` and native-title `rename_session`. The optional project Taskboard registers eight additional board-neutral task tools when enabled. `create_session` creates an empty scoped work session with validated defaults and verifies its identity/settings; no prompt, scope/permission override, automatic retry or uncertain-creation deletion is performed. `rename_session` uses OpenCode's native session update, preserves ID/history/runtime/archive state, and refuses busy, pending-input, archived or unexposed sessions. `supersede_unresolved_submission` requires fresh approval bound to the exact current guard, checks idle/pending/active-execution evidence, records a durable audit event and request UUID before one prompt attempt, and leaves the old task unresolved with an explicit operator resolution. Its `operator_authorized:true` field is client attestation, not human identity verification. Request replay is journal-bounded; generic submission is not made idempotent. Foreign-project, child, archived and OpenLive manager sessions remain excluded. Message IDs remain the prompt correlation mechanism, and permissions/questions stay in first-party Web UI/TUI. The exact client contract is [`docs/MCP-INTERFACE.md`](docs/MCP-INTERFACE.md).

**MCP Delivery A (since v0.5.67 / adapter 0.1.3):** Three additive tools bring the surface above to thirteen: `get_task_result` (bounded backward result search beyond the 100-message fast-status window), `get_message` (direct stored-message lookup), and `read_message_content` (complete visible UTF-8 text with byte ranges, revision and SHA-256). History now contains small previews, content references and explicit omissions; old `truncated` remains compatible and new `history_has_more` separates history pagination. References/search cursors are authenticated and adapter-lifetime-bound; restart requires reacquiring with stable IDs. Content changes fail explicitly rather than mixing revisions; no snapshot store or durable result index is added. Complete read responses are byte-budgeted including JSON overhead. Only existing visible user/assistant text is exposed; no tool-output export, write retry, permission-answer path or read/discussion acknowledgement. The MCP SDK/transport remain on the tested 2025-11-25 baseline. Implementation decisions, programmatic reconstruction/tunnel evidence and outstanding hosted ChatGPT acceptance are in [`PLAN_MCP_READING.md`](PLAN_MCP_READING.md).

**MCP Delivery B (since v0.5.68 / adapter 0.1.4):** `get_session_progress` adds the fourteenth tool: a read-only snapshot of tool names, states, times and parent-based task IDs from the newest 100 messages, capped at ten in-flight tools plus the last known finished step. Coverage, missing attribution, session-wide pending input and idle/stored-state mismatch are explicit; titles, arguments, output and reasoning stay private. `get_project_activity(tail:true)` selects recent matching events and returns a captured-head cursor for future ordinary reads/waits. Activity responses add a stable project/filter `filter_key`; clients maintain separate progress for each filter, while existing global cursor semantics and expiry remain unchanged. Tail is not historical consumption. No additional event subscriptions, replay store, percentages or protocol migration are added. Evidence and required hosted acceptance are in [`PLAN_MCP_PROGRESS.md`](PLAN_MCP_PROGRESS.md).

**MCP admission correction (v0.5.70 / adapter 0.1.6; stale-guard reconciliation and operator override in adapter 0.1.11):** Backend idle is separate from MCP admission tracking. `get_session` and status expose `admission`; correlated status adds active assistant evidence and does not infer a task is running from session-wide busy alone. Shared write preflight checks old receipts beyond the fast status window with bounded resumable deep reads (25 pages, ten-second deep-read budget). An exact old terminal result retires its guard; adapter 0.1.11 also retires a stale guard when a complete ordered history proves the latest later user turn has its own latest assistant `finish=stop` with completion time and no error. The old task still reports `unknown`; a later submission alone, an older completed turn followed by a newer unanswered user, or a latest turn without terminal evidence does not unlock. Activity/pending input is rechecked before admission. Idle with unresolved evidence returns `SUBMISSION_UNRESOLVED`, while actual work/concurrent writes retain `SESSION_BUSY`. Only a fresh, explicit operator decision for the exact current guard may call `supersede_unresolved_submission`; its audit/resolution record does not change the old task's actual state. Replays use a client UUID and are guarded by a write-ahead journal entry; this does not make regular sends idempotent. See [`PLAN_MCP_ADMISSION.md`](PLAN_MCP_ADMISSION.md).

**Clarification/archive integration (v0.5.72 / adapter 0.1.7 / ChatGPT skill r6):** `archive_session` is a fifteenth, generic, explicitly requested write for idle project root work sessions; it checks pending input/receipts and verifies the persisted archive timestamp. Uncertain archive responses are not blindly retried. Default list/read/write/activity confinement still excludes archived sessions. `get_session`, `get_session_history`, `get_message` and `get_task_result` accept `include_archived:true` for known archived IDs; authenticated content references from those reads carry opt-in through pagination. The independent ChatGPT-side skill proposes bounded `[KLÄRUNG]` sessions during an active conversation when the parent workstream is busy, binds origin and result IDs, validates newest identifiable OpenAI Luna/xhigh runtime before sending, and distinguishes local CLOSED from user-requested server archive. No generic agent permissions are changed; see [`docs/MCP-INTERFACE.md`](docs/MCP-INTERFACE.md) and [`integrations/chatgpt/`](integrations/chatgpt/).

**MCP file attachments (v0.5.78 / adapter 0.1.9):** `upload_attachment` accepts canonical Base64 bytes for PNG/JPEG/WebP, plain text or Markdown, validates MIME/content and returns a SHA-256-bearing, session-bound, one-use ID. `send_message.attachments` accepts at most four such IDs; arbitrary paths are rejected. Staged data is memory-only, expires after ten minutes, and is consumed when a prompt may have been admitted. Images use OpenCode file parts and require confirmed `capabilities.input` image support; text is sent as labeled UTF-8 prompt text. Limits are 5 MiB/image, 512 KiB/text, 10 MiB total per message, 32 staged references / 20 MiB per adapter; PDF is not enabled. MCP clients must be able to send the bytes themselves; an attached file visible only to the client conversation is not automatically transferred. See [`docs/MCP-INTERFACE.md`](docs/MCP-INTERFACE.md).

**MCP runtime/activity baseline (since v0.5.66):** Runtime options combine connected legacy catalogs with native enabled-model/variant metadata (custom providers bridge lazily). Partial runtime updates preserve omitted settings, validate combinations, share the MCP submission lock, check idle/pending input and verify separate v2 agent/model switches. Cross-client atomicity is not promised; partial/uncertain updates report `RUNTIME_UPDATE_FAILED` without rollback/retry. The existing adapter collects backend events and reconciles bounded durable history into private `<session-share>/mcp/activity.json`, retaining 5,000 metadata-only events with monotonic epoch-qualified cursors and bounded checkpoints. The journal survives adapter/reconnect restarts; fresh shares expire old cursors. Activity is a journal, while `get_session_status` remains current truth. Reads revalidate session exposure; waits are limited to 15 seconds plus normal backend-read deadlines. Receipts add `submitted_at`/`activity_cursor`; errors also expose machine-readable codes in `_meta["opencode-vm/error"]`. Reconciliation limits, downtime gaps, legacy empty sessions and follow-ups are recorded in [`PLAN_MCP_ACTIVITY.md`](PLAN_MCP_ACTIVITY.md).

The enabled MCP listener is fail-closed and binds only to guest `127.0.0.1`; the Lima host mapping is authenticated and verified through host `127.0.0.1` before readiness is reported. Its dedicated random token is independent of Web Basic auth and cannot be disabled by `--no-auth`. Mode-0700 session state holds a mode-0600 credential; path ownership, file type, symlinks, whitespace, and permissions are validated before use. Reconnect preserves port/token; invocation-local `--no-mcp` stops and unstages the adapter; a fresh MCP-enabled session rotates the token. Token holders can read bounded project-session history and submit prompts that may mutate the mounted project, so this is a project-scoped write credential, not harmless service metadata.

Source checkouts validate and stage adjacent `adapters/mcp/` source and build it inside the VM. Standalone scripts download only when the connector is enabled, verify the script-pinned SHA-256, reject unsafe archive members, validate the manifest, and use `~/.opencode-vm/mcp-connector/adapters/<version>-<sha256>/`. The OpenLive and MCP adapter archives are independently versioned but published under the same `v<OCVM_VERSION>` release tag; see [`docs/RELEASING.md`](docs/RELEASING.md).

**Managed OpenAI MCP tunnel (since v0.5.61; project register since v0.5.62):** `provider mcp {new|status|list|rm} openai` manages project assignments plus reusable tunnel API keys and tunnel IDs in private `~/.opencode-vm/mcp-tunnel/openai/registry.json` (schema 2), separate from model-provider auth. `new` runs in the project directory, offers stored entries with origins/current usage, or accepts `--tunnel-id` and `--tunnel-api-key` (literal, `env:NAME`, `file:PATH`; old `--api-key` alias) or `--key-id`. Project identities use canonical paths. `list` (also without `openai`) shows the global register; `status` targets cwd or `--project ID`. `rm` stops/removes only that project assignment and keeps reusable entries; `--key-id`/`--tunnel-id` remove unreferenced entries. Legacy global configuration becomes an unassigned selectable pool on migration. There is deliberately no tunnel occupancy manager or cross-project start blocking: setup warns operators to use distinct tunnel IDs for simultaneous projects. Only atomic registry edits and each project's ordinary lifecycle are serialized. After authenticated MCP readiness, its selected pair is transferred, SHA-256-pinned tunnel-client v0.0.15 is installed on demand, and a transient guest systemd service runs under the sandbox profile. Both header maps use the MCP token via file references; health uses a guest Unix socket. Tunnel failures are nonfatal to local TUI/web/MCP. Guest shutdown verifies the service belongs to this project and stops it before the adapter. Setup/list include dated, qualified ChatGPT plan guidance (official sources differ). Real macOS/Lima multi-project and ChatGPT/Voice acceptance remains outstanding; see [`docs/MCP-TUNNEL.md`](docs/MCP-TUNNEL.md).

**OpenLive integration (since v0.5.24):** `opencode-vm openlive {install|prepare|status|doctor|uninstall}` installs a macOS host shim at `~/.opencode-vm/openlive/bin/opencode`. The regular single-script path downloads the versioned adapter release over HTTPS, verifies the SHA-256 embedded in `opencode-vm.sh`, rejects unsafe archive paths and links, and atomically caches it at `~/.opencode-vm/openlive/adapters/<version>-<sha256>/`; an adjacent `adapters/openlive-acp/` tree remains the automatic development source. Later `opencode-vm update` runs refresh the required adapter automatically when the managed bridge exists; failure is explicit and stale adapters are not activated. `opencode-vm web` stages either source or release files into the session, builds source packages, or installs only locked production dependencies for precompiled release packages. OpenLive invokes the shim as `opencode acp`; the shim forwards ACP stdio to the prepared adapter inside the already-running project-specific web VM. The adapter talks to the central OpenCode server through `@opencode-ai/sdk`; Web UI, attached TUI, A2A, and OpenLive share one runtime. A persistent OpenLive manager session reports project-session totals on the first turn, can list/read sessions, and can attach the current call to an idle work session. On explicit request it can also create a work session with OpenCode's configured primary agent and OpenLive's selected model; unconfirmed creations are rolled back. Apart from explicit creation the manager is read-only, and all attachments are call-local. Attached work turns receive a voice primer which points natural review and decision requests to the default-active `besprechung` skill while leaving ordinary questions and implementation intent unchanged. Per-turn camera/screen JPEG frames are validated, bounded, and forwarded as normal OpenCode image attachments to vision-capable models; this is not continuous video, and frames remain in session history. `openlive prepare` is deprecated and directs users to `opencode-vm web`; ACP never downloads, builds, starts, or resumes a VM. All lifecycle output stays on stderr because stdout is the ACP protocol stream, and ACP stdin is reserved for the adapter. OpenLive's host credential probe is satisfied with a reserved non-secret marker only when host `auth.json` has no real entries. The marker, discovery symlink, hidden `acpCommand:opencode` setting, and adapter cache are ownership-checked and reversibly removed. Agent tools and MCPs remain VM-side; OpenLive's generic terminal remains host-side.

**Remote OpenLive (since v0.5.44; optional auth since v0.5.49):** `opencode-vm openlive remote` maps an existing macOS stub folder to an HTTPS `opencode-vm web` project on another computer. The private mode-0600 mapping selects a packaged local WebSocket client before any Lima lookup; failures never fall back locally. The existing web TLS proxy routes only `/openlive/info` and `/openlive/acp` on the same public web port to a VM-loopback gateway. Remote OpenLive inherits the web session's authentication choice: setup probes without credentials first and asks for the web Basic credential only after a 401 response. Self-signed certificates are explicitly fingerprint-pinned, and probes do not create an adapter or manager. The gateway launches only the fixed packaged adapter, while a VM-side owner lock arbitrates local and remote calls before manager/socket mutation. The workstation needs OpenLive and Node.js 22+, but no local VM, project copy, SSH access, or `init`.

**Extensions split into two subsystems (since v0.4.4):** `skills/` is for knowledge packages (pure markdown mounted as agent context); `mcps/` is for Model Context Protocol servers (tools the agent can call). Two separate registries, two separate CLIs, two separate state files. The distinction is deliberate: skills and MCPs have different lifecycles, different token-cost curves, and different security surfaces (credentials apply only to MCPs). A unified abstraction was rejected as perpetuating the debt of conflating "context" with "capability". The incoming MCP connector is a server-backed session interface for external clients; its OpenAI connection register holds project credentials/assignments, not extension packages.

**ECC integration (implicit, driven by skills):** ECC is implicit infrastructure activated by any `ecc-*` skill package. `skills_pkg_on ecc-auto` / `ecc-all` auto-clones [affaan-m/everything-claude-code](https://github.com/affaan-m/everything-claude-code) into `~/.opencode-vm/ecc/` on first enable and sets `ECC_ENABLED=1`. `skills_pkg_off` flips `ECC_ENABLED=0` once no `ecc-*` package is active anymore. When enabled, `start_session` copies the `.opencode/` payload, seeds the per-project homunculus store, and links it into the VM. `CLAUDE_PROJECT_DIR` is exported to the host project path. All ECC code paths remain gated on `ECC_ENABLED=1`.

**Skills subsystem (registry-driven since v0.4.5):** `opencode-vm skills {status|on|off|list}` is the CLI. Source of truth is [`skills/registry.json`](skills/registry.json) — declares each package with a `resolver` type (`single_bundled`, `ecc_filtered`, `ecc_all`), `default_active` / `always_active` flags, optional bundled `commands`, `mutually_exclusive_with` list, and (for ECC-style packages) filter data (universal_whitelist, language_prefixes, exclude). Five packages today: `besprechung` (default-active — session-aware discussion documents and guided dialogues, with `/besprechung` and `/besprechung-dialog`), `webimg` (default-active — image-optimization CLI tools pre-installed in base VM), `ssh-toolkit` (default-active — SSH/network workflow knowledge for the tools pre-installed in base VM), `ecc-auto` (language-filtered ~30 skills, mutually exclusive with ecc-all), `ecc-all` (~180 skills, heavy). Resolver functions (`skills_resolve_ecc_filtered`, `skills_resolve_ecc_all_pkg`, `skills_resolve_single_bundled`) all read filter data from the registry — no hardcoded whitelists in the script. `skills_resolve_pkg <pkg> <langs>` is the generic dispatch used by `skills_mount_for_session`, `doctor`, and the CLI. State: `~/.opencode-vm/skills.env` (`SKILLS_PACKAGES`, `SKILLS_DEFAULTS_VERSION`), seeded from registry `default_active` flags on first use. Defaults introduced for existing users are migrated once so a subsequent explicit opt-out remains stable.

**MCPs subsystem (registry-driven since v0.4.3):** `opencode-vm mcps {status|list|on|off|purge}` is the CLI. Source of truth is [`mcps/registry.json`](mcps/registry.json) — declares each MCP with `default_active`, `mcp_config` (type, command, optional `environment_from_credentials`), `credential_schema` (field/prompt/secret/required/default per field), `install` info (bundled/git), optional `skill_doc` path (for companion knowledge docs), and optional `agents_md_snippet` (since v0.4.12: `{source: "inline", content: ...}` or `{source: "file", path: ...}` — markdown auto-appended to the session AGENTS.md when this MCP is active). Five MCPs today: `playwright` (default on, bundled), `searxng` (default on, bundled — account-free SearXNG metasearch container installed in the base VM, systemd unit `ocvm-searxng.service`, JSON API on port 8888), `repomapper` (default off, bundled), `graphify` (default off, bundled via pipx — code knowledge-graph from [safishamsi/graphify](https://github.com/safishamsi/graphify); per-project graph persisted at `~/.opencode-vm/project-state/<hash>/graphify/graph.json`, MCP server is read-only and makes zero LLM calls; **mcrepo auto-activation since v0.4.19** — when `mcrepo.yaml` is at the project root, `start_session` exports `MCPS_FORCE_ON=graphify` / `MCPS_FORCE_OFF=repomapper` (session-only, never persisted), redirects `{GRAPH_PATH}` to `<workspace>/docs/graphify/graph.json` via a `<workspace>/.graphify-out` symlink — graphifyy 0.4.x hardcodes the output dir relative to the project (in-VM install is sed-patched at base-image build time to write to `.graphify-out` instead of upstream's `graphify-out`, so the entry stays hidden alongside `.playwright-mcp` etc.; existing `graphify-out` symlinks are auto-migrated on next session start) — and spawns `graphify watch` in the session VM so the graph rebuilds incrementally during the session; the graph plus a `GRAPH_REPORT.md` summary live committed in the mcrepo's docs folder so they ship with the rest of the documentation; the `_mcps_resolve_snippet` helper picks an mcrepo-specific `agents_md_snippet.path_mcrepo` variant when present, so the agent gets mcrepo-tailored guidance), `proxmox` (default off, interactive credential prompt, clones [canvrno/ProxmoxMCP](https://github.com/canvrno/ProxmoxMCP) host-side, installs Python venv in base VM on first session, mounts companion SKILL.md). Session injection is fully data-driven: `mcps_build_config_json <vm_home> <sess_share> <proj>` iterates `MCPS_PACKAGES`, reads `mcp_config` from registry, substitutes placeholder tokens via `_mcps_substitute_tokens` (`{VM_HOME}`, `{PROJ_HASH}`, `{SESS_SHARE}`, `{GRAPH_PATH}`), materializes credentials for MCPs with `environment_from_credentials: true`, and returns a ready-to-merge `mcp` object for `opencode.json`. `mcps_mount_skill_docs_for_session` mounts any `skill_doc` directories from active MCPs. `mcps_build_agents_sidecar <sess_share> <vm_home> <proj>` (since v0.4.12) writes `AGENTS.mcps.md` from active MCPs' `agents_md_snippet` declarations — VM-side AGENTS.md composition cats it after the Host LAN IP block. A web-mode-only sidecar `AGENTS.web.md` (written by `web_build_agents_sidecar`, appended after the MCP snippets) documents the materialized web-UI attachments; terminal sessions delete it so the web-only daemon is never advertised there. Default-active MCPs are seeded into `~/.opencode-vm/mcps.env` on first use. `mcps off <name>` wipes credentials for MCPs that have them (Proxmox); `mcps purge <name>` wipes per-project cached state (graphify graph today; extensible).

**A2A interface subsystem (host side, since v0.5.14):** `opencode-vm a2a {status|card|check}` is the CLI, implemented by `a2a_cmd` and friends (`_a2a_sessions`, `_a2a_resolve_target`, `_a2a_fetch_card`, `_a2a_card_validate`, `_a2a_rpc`, `a2a_status_cmd`, `a2a_check_cmd`). **Deliberately stateless — there is no third registry.** The A2A *server* is `start_a2a` (VM side, see the Web-mode section); this subsystem is the host-side counterpart an orchestrator's operator needs. `status` enumerates live web sessions from `~/.opencode-vm/sessions/*.env` and resolves each to its **effective** A2A URL by fetching the served Agent Card — the requested `SESS_PORT` can differ from reality when a port block had to move on a collision, so the card wins. `check` runs the full contract suite against one agent (discovery, card validation, the three auth outcomes, JSON-RPC method surface, extension negotiation, unreachable-agent and invalid-card error paths, a live `SendMessage` round trip, session binding across two turns) and finishes with a self-test that greps its own buffered output for the credential. Failure accounting goes through a temp file, not a variable: the check body runs inside a `| tee` pipeline and a counter incremented there would be lost in the subshell. The credential is resolved from the session's `auth.env` and is printed only when it equals the documented default `OCVM_A2A_DEFAULT_SECRET`. The protocol contract clients are built against lives in [`docs/A2A-INTERFACE.md`](docs/A2A-INTERFACE.md).

**Besprechung package lifecycle (since v0.5.46):** `skills_besprechung_ensure` checks the registry, skill and both commands before activation; incomplete standalone caches are repaired, complete caches work offline, and explicit update refresh failures are reported. `skills_sync_besprechung_for_session` runs on fresh starts and reconnects before OpenCode launches. Last-installed file copies under `<session-share>/besprechung-installed/` identify managed content for updates and opt-out removal; user changes are preserved. Exact original MVP files can be adopted using their recorded POSIX checksums. Same-version `update` calls retry post-update asset preparation without resetting opt-outs.

## Commands

**MCP CLI menus (since v0.5.63):** `provider mcp` offers list/add/status/rm interactively. `add` aliases `new`; OpenAI is the default provider. Interactive `rm` without a selector (with or without `openai`) asks for project connection, tunnel API key, or tunnel ID, then the exact registered entry. Guided status offers project selection. Menus support cancellation and report empty lists; explicit selectors bypass them. Bare `mcp`/`mcp rm` fail without a terminal, while the existing noninteractive `mcp rm openai` retains its current-project default. No extra deletion or permission semantics are introduced.

## Version Bumping

**Host-shell lock regression (fixed in v0.5.64):** Bash 3.2 can discard function locals before an EXIT trap on explicit subshell exit. Keep `LIFECYCLE_LOCK_LINK` and `LIFECYCLE_LOCK_CLAIM` at subshell scope (not `local`) in `mcp_reserve_host_port` and `mcp_tunnel_with_project`. `tests/mcp_lock_test.sh` runs on native macOS Bash and Linux; the release job depends on the macOS check. Existing stranded allocation-lock recovery is documented in `docs/MCP-TUNNEL.md`.

Every change to `opencode-vm.sh` **must** increment the patch version in `OCVM_VERSION` (self-update metadata block near the top of the file). The format is `MAJOR.MINOR.PATCH` — only bump the patch (rightmost) number. It can exceed 9 (e.g., `0.1.9` → `0.1.10` → `0.1.11` → ... → `0.1.100`). Example: if current version is `0.1.1`, change it to `0.1.2`. Minor/major bumps are release milestones and are decided by the user, never bumped autonomously.

## Conventions

- Write only the code the task actually needs — prefer the minimal, smallest-footprint solution over a more general or "future-proof" one. **Follow YAGNI principles** ("You Aren't Gonna Need It"): do not add abstractions, options, or machinery for hypothetical future requirements. If a need is real, it can be added when it arrives.
- **Stay in scope during execution:** a finding discovered while implementing or testing may enter the current implementation cycle only if it is required to make the agreed goal functional, to fix a regression caused by the current patch, or to pass a mandatory validation of the current scope. Everything else — improvement ideas, side issues, additional hardening — is documented and reported at the end, never implemented unprompted.
- When the work is **user-facing** (UI/UX, CLI output, prompts, messages, errors), balance YAGNI with the **Principle of Least Astonishment (POLA)**: the interface should behave the way users already expect, honoring established conventions and the context of the interaction. YAGNI governs the *feature set* (don't build what isn't needed); POLA governs *behavior* (whatever you do build must not surprise). Reconcile the two with **progressive disclosure** (minimal default surface, depth revealed when needed) and **sensible defaults over configuration**.
- The script uses `set -euo pipefail` — all errors are fatal
- Policy is stored as space-separated lists in shell variables (sourced from `policy.env`)
- LAN allowlist entries use `IP:PORT` format (e.g., `192.168.178.10:443`)
- The nftables config lives at `/etc/nftables.conf` inside the base VM and uses the `inet ocfilter` table
- Network model is Lima's default user-mode/slirp: host at `192.168.5.2`, DNS at `192.168.5.3`
- Shell scripts authored or modified in a session should be validated with `shellcheck` (pre-installed in the base VM). Focus on the lines you changed — do **not** mass-fix unrelated warnings in the rest of the file unless the user asked for a cleanup pass. If `shellcheck` surfaces a **critical** pre-existing issue outside your change (e.g. SC2086 in a security-sensitive context, SC2068 around argument passing, an unquoted `rm`/`eval`), flag it in the final report and let the user decide whether to fix it now, defer it, or accept it — never silently rewrite it.
