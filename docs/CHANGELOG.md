## 0.7.35 / MCP adapter 0.1.44 / skill 2026-10-12-r52 (local candidate, unreleased)

- **Adaptive monitor progress/investigation strategy** (task_a234c341 V2, package task_e67c39cf): the monitor engine keeps per-worker progress clocks (`worker_key` + `dispatch_receipt` episodes) with configurable starting values (first check 1 h, cooldown 1 h, long-work ladder 2 h/4 h/8 h cap) settable via the existing `create_monitor`/`update_monitor` tools (`investigation` config + task contract with optional milestone; degenerate values fail closed). After the configured first check without receipt-correlated progress, the engine runs one budgeted, strictly read-only investigation per wake — scheduled before the no-op and busy gates so a due check is never absorbed, and executed by a registry-only cheap observer that stays observation-capable while a wake blocks. Positive long-work evidence (attributable tool-progress delta on the worker's own receipt, receipt-correlated checkpoint, re-dispatch) advances the ladder; an investigation result is never progress. Errors, process loss and generation changes override the clock without a false progress reset.
- **Wake-claim recovery** (§13.8): monitor wake claims now carry owner fencing (`owner_pid`/`owner_generation`); a boot sweep releases an orphaned claim only with heartbeat evidence of the owner generation gone stale, reconciling an uncertain dispatch through the existing WAL path first (unresolved → `dispatch-uncertain` park, never a silent release). Fresh heartbeats of the owner generation and identity-less legacy claims are never released. A registry-only observer hands due investigations to the next wake via `wake_request` and makes stuck claims visible.
- **Orchestrator skill r52** (task_4ae1d182 remainder): shared three-state communication vocabulary (`CURRENT_TURN_WAIT`/`ON_DEMAND_STATUS`/`PROACTIVE_MONITORING`, new `references/communication-states.md`) with verified-hops-only notification rules — engine decisions are readable on demand, never pushed; dedicated monitoring regression rows; monitor reporting learns the new investigation states with honest non-progress wording.
- Hub remains unchanged (additive registry fields are preserved byte-stably across Hub mutations, verified by `tests/hub_crosswriter_test.py`); OpenLive unchanged; no new fallback, push, or scheduling infrastructure.
