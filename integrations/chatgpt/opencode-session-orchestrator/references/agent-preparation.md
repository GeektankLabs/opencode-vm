# Build-first preparation for authorized work

This is a client workflow, not a backend default-agent or permission change. Discover the selected connector's actual catalog and tool schemas once per segment; use only supported fields. An instruction-only skill cannot create write capability or enable a missing agent/tool.

## Select the agent from scope, independently of model profile

- **PURE_STORED_READ:** status, connection check, original-result or task-document retrieval => supported reads only; no create/update/send/model turn.
- **DEFAULT_BUILD:** authorized new/prepared work that can persist concepts/plans/Compact Context, implement files, run checks/tests or may write later; ordinary substantial new work defaults to Build. “Plan/concept” wording alone does not select Plan.
- **DELIBERATE_READ_ONLY_PLAN:** explicitly deliberate small strictly read-only clarification may use available primary Plan, with no persistence/tests/infra/write in its scope. A broader read-only task does not silently become this exception; explicit user choice remains authoritative.
- Explicit agent choice overrides the default. **PLAN_WRITE_CONFLICT:** explicit Plan plus current/anticipated file persistence => explain conflict before any create/update/send or write; ask to reconcile scope/agent, never override or try a failed write. An explicit other supported primary agent can be retained when appropriate to authorized scope; don't invent its capability. Missing/unverifiable capability is a prerequisite report, not a silently selected substitute.
- On later scope growth from Plan-only clarification to persistence, first obtain normal write authorization and fresh idle/input/runtime evidence, then Build preparation before the first write-capable prompt. Changing agent never widens remote read-only scope or approvals.

Five-role provider/model/variant selection remains separate: explicit tuple/profile wins, null-only fallback and first configured unavailable/incomplete stop unchanged. Resolve the expected model profile before preparing runtime; a configured unavailable profile is not fixed by selecting Build. An unconfigured profile preserves the current suitable tuple/backend default. Agent preparation alone never changes the chosen tuple or project profile mapping.

## Exact preparation sequence

1. **SCOPE_GATE:** establish authorized new task, explicit overrides, target connector/project and whether an existing session is suitable. Read the actual session-creation, primary-agent catalog, runtime-update and session-readback contracts. If an existing appropriate root session is supplied, reuse it; create one empty session only when needed/requested and supported, with exact identity receipt. A configured creation default may be Plan. **Never invent create_session agent/worktree parameters** or reconfigure `default_agent` to force it.
2. **AVAILABILITY_GATE:** inspect the discovered live primary-agent catalog/options; select its actual Build identifier (commonly `build`), not a guessed subagent or unavailable/disabled agent. Explicit selected agent must be verifiably available too. An existing suitable Build may be used when its actual state/capability is verified; missing catalog/readback evidence is a concrete prerequisite, not a source-checkout availability claim. Missing creation/update/readback/Build where required means stop, no alternate-session/connector/restart/permissions workaround.
3. **IDLE_GATE:** `get_session` or discovered equivalent must show the exact session idle, no pending permission/question, no concurrent write, and eligible/current receipt state under the actual admission contract. Busy/pending/unknown => no switch or send; no force/supersede or duplicate work. Capture the full current **provider_id/model_id/variant** including an omitted/none variant; retain explicit user agent and other settings. Don't switch runtime for pure stored reads.
4. **AGENT_UPDATE:** if the agent is already correct, no redundant update or new session. Otherwise use the supported partial runtime update, e.g. `update_session_runtime(session_id, agent:"build")` on a connector exposing that field. **Preserve the full current tuple and omitted settings**; backend may perform separate agent/model switches, so this is not an atomicity promise. Apply an already resolved user/profile tuple separately only when needed under the existing profile flow. If that operation fails/returns partial/uncertain, don't rollback or blindly retry; inspect actual persisted state.
5. **READBACK_GATE:** after any update, use a fresh exact session read. Require chosen primary agent **and expected full provider/model/variant tuple**, idle/no pending/no concurrent write before sending. A successful update receipt without this readback is insufficient; a tuple drift/missing metadata or uncertain readback => report **AGENT_PREPARATION_UNVERIFIED**, zero prompts. For an uncertain update, one exact readback may establish the desired state; if it does, proceed without retry, otherwise keep blocked. Never silently adopt the new tuple. A partially changed runtime is disclosed, not claimed restored.
6. **SEND_ONCE:** send the one authorized task using the actual discovered tool after all gates, with its scope/task/C-P/source owner/return information. Correlate actual submitted user receipt; lost send follows existing receipt reconciliation, no second prompt. Even a READ-ONLY remote analysis send is a write-capable connector operation; Plan is not a technical sandbox. Keep runtime profile/agent preparation, execution permission, task scope and business PASS distinct.

Preserve the established Build+tuple on normal same-work-item follow-ups, rechecking idle/pending/receipt gates where required; don't change runtime for every status/poll/result read. Agent switching doesn't authorize new workers, session archive, Board Done, integration, release or deploy. Explicit user conflicts and true security/host controls remain operator handback, not native Question/permission autoanswer.

## Pre-dispatch runtime gate (every new dispatch, including follow-ups)

Treat the session's current runtime as **never proof** of the intended profile. Before every new task dispatch — a fresh order and equally a follow-up turn — resolve the matching **enabled** project model profile fresh from the **current** project policy (`get_recommended_runtime` / `get_project_model_policy`), then explicitly set the session runtime with `update_session_runtime` and require a full provider/model/variant readback **before** `send_message`. A cached, historical or remembered policy revision is never evidence; re-read the live policy on each dispatch.

- Do not mutate a healthy session that is actively working. When the desired runtime differs from a busy session, never issue a mid-turn send or an unsupported mid-turn switch; wait for a controlled idle boundary (verified idle/no-pending) and apply the runtime there.
- An unconfigured profile keeps the existing suitable session tuple; a configured-but-unavailable or incomplete mapping is a named blocker, never a silent substitute.
- A generic or inconclusive answer earns at most the bounded supported read-retry (see [Pause and Go](pause-go.md)); beyond that, report a blocker instead of re-asking or re-sending.
- Correct an evidenced wrong inherited default explicitly after a failed start; never build on an unverified inherited runtime, and never rely on a historical revision of the policy.

## Checks and external acceptance

The regression catalogue and source-bound scripted tool-call traces cover configured Plan creation then Build, existing Build reuse, explicit Plan/persistence conflict, deliberate read-only Plan and authorized scope growth, provider/model/variant preservation, busy/questions/permissions, missing catalog/Build/update/readback, uncertain/partial updates and profile-unavailable stop. Synthetic fake-connector traces check order/actions/gate failures, not live ChatGPT agent behavior or permission enforcement; packaged instructions must be separately accepted on the actual connected surface.
