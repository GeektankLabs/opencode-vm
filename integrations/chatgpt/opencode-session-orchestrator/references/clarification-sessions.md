# Bounded clarification sessions

Use for a fresh, independent technical or factual question related to an identified workstream, especially a code or planning-file detail when that workstream is busy with another task. During an active conversation, offer this path once when useful: name the specific question and its origin. If the user already asked to clarify it, proceed within that authorization. A status check, incidental observation or uncertain receipt alone is not authorization to run new research. Never resubmit the blocked original task through a side session or bypass approval.

## Start

1. Identify the connector/project and the origin's **title and session ID**; read only the relevant decisions, files, plan locations, results and current state. Keep independent questions in separate sessions rather than reusing an old `[KLÄRUNG]` topic.
2. Keep a short clarification separate from broader architecture or multi-decision planning. For the latter, offer a named concept workstream with a suitable stronger available model (notably Sol) instead of treating it as a normal clarification.
3. Discover the real `openai` model catalog before creation. Select the **newest identifiable Luna model** supporting `xhigh` only if it is also the newest Luna offered: do not silently fall back to an older Luna when the newest lacks `xhigh`. `gpt-6-luna` is the current example, not a permanently pinned model. Compare numeric release components, not lexical model IDs; ambiguous version/alias order, truncated catalog or unavailable provider/variant means stop and explain the missing choice. Do not invent a provider/model ID or variant that is absent from the selected connection.
4. If session creation and runtime switching are supported, create one empty root session titled `[KLÄRUNG] <short concrete title>` (within the connector's title limit). Capture its exact ID. Set `provider_id:openai`, the chosen Luna `model_id` and `variant:xhigh` via the supported runtime-update tool; reread the session and require an exact match **before** any prompt. Do not automatically repeat uncertain creations/partial updates. A connector without these capabilities cannot fulfill this default workflow; explain the limitation rather than dispatching an unrestricted alternate task.
5. Send **one** bounded handoff, never just the isolated question. Include the origin title/ID, concrete question, short reason/background, current known state, relevant task/message/result/session IDs and file/plan/component locations, decisions explicitly marked as settled unless new evidence contradicts them, applicable scope limits, requested result format/decision criterion, and return destination. Select only question-relevant context; do not paste the entire original history. An instruction like "read only" does not itself enforce backend permissions: if strict read-only execution is required, use an actually restricted capability or disclose the limitation instead of claiming enforcement.

## Return or branch

Read a terminal answer's complete relevant visible text, including caveats; intermediate tool completion alone is not a final answer. Record its receipt/result IDs and conclusion or remaining uncertainty against the origin in the working registry. Return the finding to the user and, when required, to the original/planning workstream using a short summary plus the clarification's ID and source result. If that workstream is busy, retain a prepared-but-unsent handback and do not interrupt it or pretend it received the answer. Keep the pending handback visible until delivery is confirmed. `CLOSED` follows successful assignment/handback, not just an idle observation; closed topics leave ordinary open-work overviews.

If a new topic needs concept work, stop planning inside `[KLÄRUNG]`. Ask whether to continue in the origin once it is available or start a clearly named new concept session using a suitable available stronger model. A new session's handoff links **both** the original title/ID and the clarification title/ID and explains the derived question; the user chooses that branch. No automatic reroute of a denied or unresolved original task.

Archiving is a separate, **explicitly requested** operation, available for any eligible project work session when the connector exposes `archive_session`. Archive a completed clarification only after its relevant answer and return link are secured. Verify the archive result; an uncertain response is not success and must not be retried blindly. Without the capability, call the topic `CLOSED` locally, not archived. On compatible opencode-vm connectors, archived sessions disappear from ordinary lists and default reads; recover their known IDs with `include_archived:true` on `get_session`, `get_session_history`, `get_message` or `get_task_result`. Content references from those opted-in reads continue with `read_message_content`. Preserve the origin/clarification IDs for later topic tracing. Do not assume another connector supports these fields or that a client-side registry persists across chats.
