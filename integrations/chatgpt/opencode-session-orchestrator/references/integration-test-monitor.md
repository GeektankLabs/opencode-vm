# Long integration/system-test Monitor policy

Use the shared [Monitor Tasks](monitor-tasks.md) setup, lifecycle, serialized wakeup, receipt/checkpoint and deferred-provenance contract. This is a policy, not a second scheduler. There are three logical objects: the technical Integration-Test Task/session (possibly already running), a separate Monitoring/Master Task, and its recurring Scheduler Auftrag. Reuse existing task/session/message IDs; no engineering/run Board card per retry.

## Worker and manager boundaries

The test worker remains conservative/fail-fast: run the agreed test/acceptance, retain useful failure state and report real evidence. The stronger monitoring manager may classify results, request diagnosis, bounded preauthorized harness/test-environment fixes, focused regression, and evidence-based Resume vs Fresh. It cannot alter product, architecture, schema/data, security/trust/permission or acceptance semantics to achieve PASS; such a decision parks with exact `INPUT_REQUIRED`, options, completed and paused work. Do not weaken an assertion or clean/reset unknown work to unblock a test.

Setup fixes the test command/config/target/base, environment/fixture identity, approved repair surfaces and resource scope, unchanged PASS criteria, retention/resumption mechanism, time/run/note budget and operator boundary. Apply the core Lean Spot-Check to a materially unknown shared test resource, not an assumed enterprise environment. A worktree does not isolate an external test database/service.

## Classify with hard evidence

Read the exact correlated terminal original using [content protocol](content-protocol.md), not a preview/tool completion/idle signal. PASS requires complete relevant visible evidence of commands, exit/test counts/assertions, target/base/environment and configured integration/acceptance criteria; then `COMPLETE_PASS`. FAIL means the actual test's configured criteria demonstrably failed. BLOCKED means a named prerequisite/decision/input prevents the run. An aborted run, generation timeout or lost report is ABORTED/UNKNOWN, neither PASS nor an invented product FAIL. Pending permission/question is session-wide operator attention, not an autoanswer path. A live test process independent of a finished model turn must also be reconciled before any rerun; idle alone proves nothing about that process.

Unclear cause => one targeted read-only diagnosis assignment, with suitable available worker profile under the [runtime rules](../SKILL.md#project-runtime-profiles-for-new-authorized-work). Substantial unclear diagnosis generally resolves `deep`; known-plan tests use `execution`, ordinary bounded repair `standard`, unless explicit user choice prevails. Do not create another session for the same work to evade busy/uncertain/input. The profile does not make arbitrary execution read-only; preserve the diagnosis scope explicitly.

## Fingerprint, counters and progress

Fingerprint stable, sanitized components: test/harness identity + failing test/assertion/stable stack location + normalized failure class/code + relevant config/environment/fixture versions. Exclude timestamps, transient IDs/random ports and unrelated text. A superficial new message or minor wording change with the same root signature is practically the same fingerprint. A repair's own changed harness revision does not automatically make a recurring original failure a new fingerprint. Record equivalence rationale; uncertain equivalence is conservative, not a fresh counter.

Default: **at most two autonomous repair cycles for the same/practically same fingerprint without material progress**. A cycle is one bounded repair attempt plus focused regression/readback. Diagnosis alone is not a cycle. Reserve a cycle when its repair is admitted; an uncertain repair reserves it until reconciled, so missing regression or crash cannot create unlimited repairs. Release only proven non-admission, never erase an attempted fix merely because it failed. After two attempts with the same failure and no progress, `PARKED_INPUT_REQUIRED`; no third fix. Keep historical per-fingerprint counts and pending phase across wakeups; A→B→A does not forget A.

Material progress is attributable evidence that the original failure is resolved or genuinely narrowed under unchanged acceptance/target conditions, not a new timestamp, different model, unrelated passing test or softer assertion. Focused PASS permits continuation, but if the full run reproduces the original failure without further progress, retain that failure's cycle history. Reset its no-progress episode only with recorded evidence that it was resolved or materially progressed; a genuinely different root cause has a distinct fingerprint under the total horizon/run budget. Explicit setup can choose a stricter or otherwise operator-approved cap, never silently raise it mid-run.

For an exact confirmed terminal transient provider/generation/infrastructure error, default at most **one continuation per unchanged failure episode**, only when old receipt/result and actual test state are reconciled, target idle/no pending input, scope authorizes it and resume is safe. Repeating it without progress parks/diagnoses; it is not a repair-counter loophole. No retry of `SUBMISSION_UNCERTAIN`, uncertain note/create/runtime update or incomplete result: exact readback/reconciliation first.

## One policy step per wakeup

1. RUNNING/busy -> no-op; no new orders. Permission/question -> operator attention/park. Uncertain admission/result/connection -> reconcile or park, not retry.
2. Verified FAIL/BLOCKED with unknown cause -> bounded diagnosis; read its original result on a later wakeup.
3. Proven approved harness/environment cause -> one narrow reversible fix with [worktree owner/actual tool target](worktree-ownership.md), exact diff/base and allowed surfaces. Product/security/schema/acceptance change -> park instead.
4. Repair result -> focused regression first; no full rerun in the same management wakeup. Read exact regression command/result, relate it to the original failure and update reserved/completed cycle/progress evidence. Failed same fingerprint at the cap -> park.
5. Focused regression verified -> Resume if the original run has a real resumable checkpoint, compatible current target/environment/base, preserved state and no live process/receipt/double-submit ambiguity. Otherwise choose controlled Fresh only after the old run is reconciled terminal and the environment/retention/reset steps are specifically allowed. Fresh is a new test attempt with new submitted message ID in the same appropriate session; preserve prior IDs/evidence. “Fresh” does not mean a new Board task or clean/reset permission.
6. Follow shared checkpoint/readback rules after the single action: actual delivery, original result IDs/coverage, lifecycle, diagnosis/edits/focused tests, fingerprint/cycles/progress, owner/base, why no more action is allowed and next permitted step.

Park/final handoff must let the operator reconstruct the last actual run/receipt/outcome, what was diagnosed/changed/tested, why autonomy stopped, exact decision/options, retained state and safe next step. The scheduler may keep waking cheaply. Free-form later Management Notes do not authenticate resume; use the shared downstream-QC boundary and existing interactive operator revalidation flow.
