# Project-board lookup and remainder preview

Use this reference only when the user's selected connection actually exposes compatible project-board tools. The board is a project-local inventory of **outcomes still owed**, not a copy of every agent plan, session, message or tool call. Do not assume that an attached connector exposes a board, that its schemas match opencode-vm, or that a taskboard task is an MCP execution task.

Read the [task compact context](task-compact-context.md) convention when a known board task's work spans multiple agent iterations or faces an interrupted handoff.

Read the [task concept plan](task-concept-plan.md) convention for complex or conceptually rich board tasks that need a persistent concept and planning document alongside the compact context.

## Find before creating

1. Preserve the selected connector/project. If the user supplies a stable `task_id`, use `get_project_task` directly. If a session is known, use a discovered `list_project_tasks(session_id=...)` for reverse lookup. Otherwise search title/description with `query`, narrowing by a supported status when useful. Use the tool's **actual** schema; do not invent a semantic-search parameter, cursor or global project scope.
2. Treat a successful complete list as the evidence boundary. opencode-vm's initial board search scans the whole project-local upstream list only within a fixed limit and has **no search pagination**. `TASK_SEARCH_INCOMPLETE` means coverage is unknown: a smaller status-filtered search may help, but a zero-match from an earlier partial attempt is never proof of absence. Do not create a duplicate simply because a search failed or overflowed.
3. Reuse an existing card when the new request is another implementation, review, verification, fix or resumption of the same independently testable outcome. A new card needs a separately prioritizable/closable outcome or work that must persist beyond the current execution context. Internal agent checklists, test steps and every technical finding are not automatically board cards.
4. Without board tools, keep the normal session workflow. State that board-based deduplication or reverse lookup cannot be verified; do not fabricate task IDs or silently make a new board somewhere else.

## Propose classification when there is persistent work

- A discussion, hypothetical idea, internal agent step or finding without an independently trackable remaining outcome needs no board proposal. When a concrete follow-up emerges, discover `list_board_projects` (if available) and search the full repository board before proposing a destination. `project_id` is a legacy Board Project selector, **not** the repository scope; prefer `board_project_id` where supported. A filtered search never proves absence in other Board Projects. Do not assume a connection exposes the new tools.
- If the same outcome already has a card, propose a specific extension of that card and a reference to the relevant message/result, not a duplicate. Read the old description first; show the new obligation and its proposed Board Project to the user. Re-read immediately before a confirmed `update_project_task`; if changed, stop and ask for a revised decision. A sidecar comment is not an upstream-visible replacement for the task description.
- For a separately closable outcome within an existing workstream, propose a ticket there. For an independent enduring workstream likely to hold multiple outcomes, propose a named Board Project (with a unique 1–5-character prefix) and optional first tickets. For small/unclear but genuinely persistent work, propose a ticket in the default collection (`Inbox`). Offer the classification once, briefly explaining why; respect a declined or corrected suggestion during that conversation unless the outcome changes.
- All board mutations need a concrete user instruction or acceptance of the specific proposed package. An explicit “create X in Y” already authorizes X in Y; do not ask again per ticket. If the board is empty, include first-time `Inbox`/`INBOX` setup in the confirmed package before creating its first ticket; **never** create a Board Project or ticket on a read or while merely proposing. An existing default with a different name/prefix stays as it is; collisions or unavailable tools require a user choice, not a silent rename/fallback. Teams are optional in the unchanged UI.
- Moving a confirmed default/Inbox ticket into an existing workstream is a separate `reclassify_project_task` operation, not `transfer_project_task` (which is a different, unavailable scope transfer). The same operation now also accepts a Board Project→Board Project move between any two existing active workstreams in this repository. Confirm the particular destination, read source and target IDs, generate one UUID `request_id` and preserve it with the exact fields on replay. For errors or lost replies, inspect `get_task_transfer_status(request_id)`; do not generate a second request, infer completion from a technical `done` staging copy, or create another ticket. A repeated request whose `expected_source_board_project_id` no longer matches the live source is refused as `TASK_TRANSFER_CONFLICT`; a missing source retires the journal as `aborted` and any replay with the same UUID fails closed. A `TASK_TRANSFER_UNRESOLVED` requires reconciliation of the original request; the source and target may briefly coexist while the target is visibly `transfer-pending`. Success changes the native key/ULID but retains the public task ID and links. Tickets with native dependencies are unsupported in v1.
- A session or agent finishing never automatically closes a board ticket. Read outcome and evidence before offering `done`; a specific user instruction or accepted proposal authorizes a status change, followed by readback. No UI/MCP-wide compare-and-swap is available: report a newly discovered conflict rather than asserting an atomic edit.

## Task compact context in board work

A board task with a maintained compact context (see the [task compact context](task-compact-context.md) convention) integrates as follows:

- **Before the status transition**: propose the compact context for a multi-iteration task and confirm its first write before assigning creation to the executing agent. No file is created on a board read; a declined offer leaves `todo` work unchanged. A later user-confirmed transition into `in_progress` invokes the combined-file rule below; do not silently waive it because of that earlier decline.
- **Every task-bound handoff**: include the exact path of each established file in the message to the executing agent. A new executing context gets the full one-time care instruction; normal substantive same-context follow-ups get only the short reminder with paths; QA checkpoints get the fuller refresh. Tiny read-only checks need no maintenance reminder, and a pure status read needs no agent prompt. After a chat restart, use `get_task_documents` when available to recover roles/paths rather than guessing. For an old unregistered task, check the default path only in authorized work; absence is unconfirmed, not invented content.
- **Introductory quality checks**: compare actual context content and its ~5k/~7.5k/~10k-token one-file policy early after first substantive work and after longer/larger iterations or several substantive follow-ups against board/original results. Include the policy refresh in an authorized checkpoint request; use `get_task_documents`/`read_task_document` directly when available, otherwise request exact text in the agent result. Stale/incomplete content goes to the executing agent for correction in the next authorized work request, not to the manager as routine editor. See the [quality checklist](task-compact-context.md#orchestrators-introductory-quality-checks).
- **Remainder preview**: a context can inform a preview only when its content is actually available and checked against board/evidence. The task's remaining obligation still comes from the board and evidence; a context or link alone is not completion proof.

## Task concept plan in board work

For complex or conceptually rich tasks, the [task concept plan](task-concept-plan.md) is the durable concept/architecture/decision/test document; the compact context is the working-state pointer. They are kept complementary, not duplicative.

- **When to use**: a substantive architecture, design, requirement, interface, implementation or test concept can justify a plan already in `todo`. On a confirmed `todo` -> `in_progress` transition, this workflow requires both files even when the initial plan is modest; omit inapplicable sections rather than fabricate complexity.
- **Mandatory initialization before `todo` -> `in_progress`**: use the ordered sequence below. The existing Board API and project files are not one transaction; never move the Board task on the strength of a submitted prompt alone.
- **Every plan-backed task handoff**: include its plan path; when the context is established include that path too. At initialization/new executing context convey the full roles, update triggers and size/split policy once. Normal substantive work (including diagnosis/tests with possible findings) gets the one-line reminder; only new conceptual findings change the plan. Keep the main plan as canonical index when ~40k tokens require task-bound detail files; the context remains one file and cites the plan, not its entire rationale.
- **Introductory quality checks**: check both files together when initializing or handing over, then at the respective substantive milestones. Refresh the agent's size/quality duty in the authorized QA request; directly read the registered plan main file and relevant indexed detail documents when supported, comparing Board and original result. Fall back to complete agent-supplied text only when direct reads are unavailable; incomplete text is pending, not proof. Corrections go to the executing agent in the next authorized follow-up. See [concept-plan quality](task-concept-plan.md#orchestrators-introductory-quality-checks) and [context quality](task-compact-context.md#orchestrators-introductory-quality-checks).
- **Closure**: after verified business completion, request the plan `Status: accepted` (or `superseded`) only as an authorized project-file write; otherwise report that update pending. Neither board status nor agent completion silently edits the plan.

### Ordered transition and recovery

1. Discover `add_task_document_bindings` (preferred), `get_task_documents` and the Board move tool; only if the bundle tool is absent discover fallback `register_task_document`. Read the exact Board task and verify `todo`; obtain authorization for the specific move and initialization package. Keep it `todo`. Send the executing agent one authorized write-capable request with the [full care instruction](task-concept-plan.md#initialization-instruction), both task-ID paths and the ticket's conceptual starting state. Reuse matching documents; a different `Task-ID` is a collision, not permission to overwrite.
2. Read the correlated original result and require the agent to identify each **role, task ID and actual path**, ending with the literal `CONCEPT_READY:` label. If the result is missing/uncertain or file creation failed, stop with Board still `todo`; do not blindly resend. The two project files survive any later failure. The agent's `CONCEPT_READY` is the start of the orchestrator's follow-through, not its end; the orchestrator still has to verify, register and read back before the Board moves. See [Initialization follow-through](initialization-follow-through.md) for the labelled checkpoints (`CONCEPT_READY`, `REGISTERED`, `BOARD_MOVED`).
3. Prefer one `add_task_document_bindings(task_id, compact_context, concept_plan)` call for both verified main files. All files/conflicts are checked before one sidecar commit; exact replay adds nothing. On error/conflict stop with Board still `todo`, never fall back to replacement. Only when the new tool is absent use `register_task_document` for each main role without `expected_path`; preserve partial success and register only the missing role on authorized resume. Authorized `concept_detail` still uses the old tool. Read `get_task_documents` back: require both main roles, `state:available`, exact paths and revisions before `REGISTERED`. Generic `artifact_refs` are not substitutes.
4. **Only then** call the discovered Board move tool for `in_progress`; read the exact task back. If the move fails or its response is uncertain, keep existing files/references, inspect current Board status before any retry and do not recreate or duplicate them. `todo` can be retried under the existing authorized package once non-delivery is established; `in_progress` means the move already occurred. Other statuses/conflicts require a new decision. There is no server-side Board/filesystem transaction or cross-client UI guarantee.

### Orphan-files recovery

When matching files already exist at canonical paths from an interrupted run, do **not** ask the executing agent to recreate them and do **not** rename them. Detect → verify each `Task-ID` → reuse → preferred add-only bundle (register fallback only if absent) → `get_task_documents` → separate Board move/readback. A foreign `Task-ID` or conflicting main binding stops the run; no overwrite or retarget.

With an older connector lacking registration tools, stop before a newly requested `todo` -> `in_progress` transition and explain the missing prerequisite instead of silently moving the Board task through the legacy path. Existing unreferenced tasks remain readable and usable; an already `in_progress` task without both files needs separately authorized backfill, not a fabricated status transition.

### Direct task-document reads

On capable connectors, `get_task_documents(task_id)` returns semantic roles and current availability/revisions; `read_task_document(task_id, role, path?, offset?, revision?, max_bytes?)` reads only registered task-ID-marked Markdown. For later pages keep the returned `revision` and next byte offset; on `TASK_DOCUMENT_CHANGED`, discard the old pages and restart at zero. `concept_plan` names the main/index file; `concept_detail` selects a registered task-ID-bound detail file, never a replacement main plan. Missing/invalid references and paths are explicit errors. These reads neither mutate Board state nor start an agent.

For an Executive Summary, progress, blockers or next step, read `compact_context` first and answer from its relevant sections. Read the main `concept_plan` only for concept, architecture, intended implementation or test depth; fetch indexed `concept_detail` files only for relevant questions. Attribute actual work, test results and completion to original session results, not the task documents. When direct read tools are unavailable, use stored Board/session evidence and disclose the document gap; use the existing agent-mediated exact-text QA fallback only within authorized work.

## Management notes

Use `add_task_management_note(task_id, note)` only for an explicitly requested short management follow-up on an existing task. Read the exact task, append the authorized note once, then use `get_project_task` to verify its visible description and retained fields. Each call adds a `Management Note:` block; identical text is not deduplicated. On lost/uncertain response, reconcile by readback and report uncertainty if attribution is ambiguous; never blindly retry or replace the description via `update_project_task`. Missing note capability is an explicit gap, not a general edit fallback.

The description-only GET/PUT serializes cooperating note writers; no upstream CAS protects against parallel UI/general edits. This accepted boundary is not a global loss-free append guarantee. Both tools' readOnly/destructive/openWorld hints are false; note idempotent is false and binding idempotent is true. Hints neither authorize writes nor guarantee suppressed host approval UI. Notes do not move status. Executive Summary/status/remainder reads and initialization create no notes; durable context stays in the task documents.

## Keep work and execution separate

- Board columns describe `todo`, `in_progress`, `done`; a blocked card remains work in progress. Board WIP counts cards, not active agent sessions. A session or tool ending does **not** move a card to Done.
- Before reporting a business outcome, read the relevant original result through the content protocol. Distinguish achieved, verified, open and blocked/decision-dependent work. Prefer ID/reference pointers to copying long reports into the board.
- If board linking is in the user's authorized work package, `link_task_to_session` may record the exact session and optional submitted `message_id`, short result or artifact refs. Multiple messages of one session stay separate links. A session ID must belong to the selected project; an accepted prompt is not yet a verified result. The initial board exposes generic links, **no** built-in implementation/review/analysis role or automatic result synchronization.
- For "what is this task linked to?", use the task's `session_ids` and, where offered, complete `links` from `get_project_task`. For "which tasks belong to this session?", use the session filter. A link alone does not prove the associated message succeeded.
- Until the board exposes actual transition timestamps, `updated_at` is merely the latest ticket edit, **not** a reliable work-start date, work-item age or cycle-time measurement. Soft WIP means favoring finishing/unsticking/clarifying existing outcomes before unnecessary new work, not blocking `send_message` through a new admission policy.

## Read-only remainder synthesis (phase 1)

When the user asks what is still open, or several cards appear to describe the same future result, offer or produce a **preview**. This is a read workflow: use board reads and already stored session/message/result reads; do not create, move, update, comment, link, archive or send prompts merely to produce the preview. An incomplete board scan, missing result or partially read report limits the conclusion explicitly.

For each relevant original card, extract: outcome reached, actually verified, remaining obligation, decision/risk, and available message/result/artifact references. Group **remaining future outcomes**, not past task labels. Show a compact mapping such as:

| Existing task ID | Verified / still open / unknown | Evidence and coverage | Suggested remaining outcome |
|---|---|---|---|

Check every known open obligation has a named proposed home, or clearly mark it unresolved. Distinguish a plausible `completed`, `superseded` or `dropped` **suggestion** from an existing backend field: those resolution and successor fields are not part of the initial board contract. Do not delete, close, merge, mark Done, or discard a card in phase 1. Decisions to drop scope or accept risk stay with the human; applying a preview is a separate authorized future workflow. Do not claim 100% coverage when search or original-result reading was incomplete.
