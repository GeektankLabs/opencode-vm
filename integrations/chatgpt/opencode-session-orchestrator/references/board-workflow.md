# Project-board lookup and remainder preview

Use this reference only when the user's selected connection actually exposes compatible project-board tools. The board is a project-local inventory of **outcomes still owed**, not a copy of every agent plan, session, message or tool call. Do not assume that an attached connector exposes a board, that its schemas match opencode-vm, or that a taskboard task is an MCP execution task.

## Find before creating

1. Preserve the selected connector/project. If the user supplies a stable `task_id`, use `get_project_task` directly. If a session is known, use a discovered `list_project_tasks(session_id=...)` for reverse lookup. Otherwise search title/description with `query`, narrowing by a supported status when useful. Use the tool's **actual** schema; do not invent a semantic-search parameter, cursor or global project scope.
2. Treat a successful complete list as the evidence boundary. opencode-vm's initial board search scans the whole project-local upstream list only within a fixed limit and has **no search pagination**. `TASK_SEARCH_INCOMPLETE` means coverage is unknown: a smaller status-filtered search may help, but a zero-match from an earlier partial attempt is never proof of absence. Do not create a duplicate simply because a search failed or overflowed.
3. Reuse an existing card when the new request is another implementation, review, verification, fix or resumption of the same independently testable outcome. A new card needs a separately prioritizable/closable outcome or work that must persist beyond the current execution context. Internal agent checklists, test steps and every technical finding are not automatically board cards.
4. Without board tools, keep the normal session workflow. State that board-based deduplication or reverse lookup cannot be verified; do not fabricate task IDs or silently make a new board somewhere else.

## Propose classification when there is persistent work

- A discussion, hypothetical idea, internal agent step or finding without an independently trackable remaining outcome needs no board proposal. When a concrete follow-up emerges, discover `list_board_projects` (if available) and search the full repository board before proposing a destination. `project_id` is a legacy Board Project selector, **not** the repository scope; prefer `board_project_id` where supported. A filtered search never proves absence in other Board Projects. Do not assume a connection exposes the new tools.
- If the same outcome already has a card, propose a specific extension of that card and a reference to the relevant message/result, not a duplicate. Read the old description first; show the new obligation and its proposed Board Project to the user. Re-read immediately before a confirmed `update_project_task`; if changed, stop and ask for a revised decision. A sidecar comment is not an upstream-visible replacement for the task description.
- For a separately closable outcome within an existing workstream, propose a ticket there. For an independent enduring workstream likely to hold multiple outcomes, propose a named Board Project (with a unique 1–5-character prefix) and optional first tickets. For small/unclear but genuinely persistent work, propose a ticket in the default collection (`Inbox`). Offer the classification once, briefly explaining why; respect a declined or corrected suggestion during that conversation unless the outcome changes.
- All board mutations need a concrete user instruction or acceptance of the specific proposed package. An explicit “create X in Y” already authorizes X in Y; do not ask again per ticket. If the board is empty, include first-time `Inbox`/`INBOX` setup in the confirmed package before creating its first ticket; **never** create a Board Project or ticket on a read or while merely proposing. An existing default with a different name/prefix stays as it is; collisions or unavailable tools require a user choice, not a silent rename/fallback. Teams are optional in the unchanged UI.
- Moving a confirmed default/Inbox ticket into an existing workstream is a separate `reclassify_project_task` operation, not `transfer_project_task` (which is a different, unavailable scope transfer). Confirm the particular destination, read source and target IDs, generate one UUID `request_id` and preserve it with the exact fields on replay. For errors or lost replies, inspect `get_task_transfer_status(request_id)`; do not generate a second request, infer completion from a technical `done` staging copy, or create another ticket. A `TASK_TRANSFER_UNRESOLVED` requires reconciliation of the original request; the source and target may briefly coexist while the target is visibly `transfer-pending`. Success changes the native key/ULID but retains the public task ID and links. Tickets with native dependencies are unsupported in v1.
- A session or agent finishing never automatically closes a board ticket. Read outcome and evidence before offering `done`; a specific user instruction or accepted proposal authorizes a status change, followed by readback. No UI/MCP-wide compare-and-swap is available: report a newly discovered conflict rather than asserting an atomic edit.

## Keep work and execution separate

- Board columns describe `todo`, `in_progress`, `done`; a blocked card remains work in progress. Board WIP counts cards, not active agent sessions. A session or tool ending does **not** move a card to Done.
- Before reporting a business outcome, read the relevant original result through the content protocol. Distinguish achieved, verified, open and blocked/decision-dependent work. Prefer ID/reference pointers to copying long reports into the board.
- If board linking is in the user's authorized work package, `link_task_to_session` may record the exact session and optional submitted `message_id`, short result or artifact refs. Multiple messages of one session stay separate links. A session ID must belong to the selected project; an accepted prompt is not yet a verified result. The initial board exposes generic links, **no** built-in implementation/review/analysis role or automatic result synchronization.
- For "what is this task linked to?", use the task's `session_ids` and, where offered, complete `links` from `get_project_task`. For "which tasks belong to this session?", use the session filter. A link alone does not prove the associated message succeeded.
- Until the board exposes actual transition timestamps, `updated_at` is merely the latest ticket edit, **not** a reliable work-start date, work-item age or cycle-time measurement. Soft WIP means favoring finishing/unsticking/clarifying existing outcomes before unnecessary new work, not blocking `send_message` through a new admission policy.

## Read-only remainder synthesis (phase 1)

When the user asks what is still open, or several cards appear to describe the same future result, offer or produce a **preview**. This is a read workflow: use board reads and already stored session/message/result reads; do not create, move, update, comment, link, archive or send prompts merely to produce the preview. An incomplete board scan, missing result or partially read report limits the conclusion explicitly.

For each relevant original card, extract: outcome reached, actually verified, remaining obligation, decision/risk, and available message/result/artifact references. Group **remaining future outcomes**, not past task labels. Show a compact mapping such as:

| Existing task ID | Verified / still open / unknown | Evidence and coverage | Suggested remaining outcome |
|---|---|---|---|

Check every known open obligation has a named proposed home, or clearly mark it unresolved. Distinguish a plausible `completed`, `superseded` or `dropped` **suggestion** from an existing backend field: those resolution and successor fields are not part of the initial board contract. Do not delete, close, merge, mark Done, or discard a card in phase 1. Decisions to drop scope or accept risk stay with the human; applying a preview is a separate authorized future workflow. Do not claim 100% coverage when search or original-result reading was incomplete.
