## Problem and target outcome

The `opencode-session-orchestrator` skill already describes the correct atomic fail-closed sequence for a user-confirmed `todo` -> `in_progress` transition (see `references/board-workflow.md` §"Ordered transition and recovery", `references/task-concept-plan.md` §"Mandatory initialization on `todo` -> `in_progress`", `references/regression-scenarios.md` §"Ordered initialization, direct document reads and executive view", and the SKILL.md section "Initialize concept plan + compact context on `todo` -> `in_progress`"). The sequence is unambiguous: keep Board `todo` → send one authorized full initialization request to the executing agent → read the agent's correlated original result → verify both files (existence, `Task-ID`, path, content) → register both semantic task-document roles (`compact_context`, `concept_plan`) → read them back via `get_task_documents` and require both `state:available` → only then call the discovered Board move tool → read the Board task back.

In two real initializations — `task_954ff35f-5228-5fb1-8390-cb4bf210e083` (Disk-Resize-UX) and `task_4ae1d182-0da2-53c1-97e6-081f66c27246` (Monitoring-Zusagen) — the executing agent returned `CONCEPT_READY` with both files created and identified at their canonical paths. The orchestrator then stopped. The Board task remained `todo` even though files existed, and no `compact_context` / `concept_plan` semantic registration was ever recorded. The user's authorized transition was effectively rolled back by the orchestrator treating the agent's intermediate checkpoint as a terminal success. The same failure shape (files exist on disk, Board still `todo`, no semantic registration) is also the natural state of an interrupted authorization: an authorized write-capable initialization request was sent, the agent completed and returned, but the orchestrator never completed the remaining orchestrator-side steps. Without explicit guidance, a future orchestrator run on a similarly-positioned task is likely to either repeat the early stop, or to advance the Board without the underlying registrations.

Goal: in the orchestrator skill, make the post-`CONCEPT_READY` follow-through semantics atomic and explicit. `CONCEPT_READY` is a labeled checkpoint returned by the executing agent, not a terminal state. The orchestrator must subsequently complete verification → registration → document readback → Board move → Board readback, or fail closed with Board still `todo` on any genuine error. Recovery from files that already exist at the canonical paths but were never registered must be an explicit supported path (reuse the existing files, register them under the same path/Task-ID). Regression coverage must reflect the actual sequence — file existence, both registrations, both `available` readbacks, Board move, Board readback — and not just text markers. The result is that a user-confirmed `todo` -> `in_progress` transition either completes atomically end-to-end, or visibly stops at the last successful step with a precise reason.

This change is documentation + vocabulary + regression rows + one synthetic flow-level test. It introduces no new MCP tool, no scheduler, no board mutation primitive. The orchestrator skill stays a client-side instruction package.

## Requirements and acceptance criteria

1. **`CONCEPT_READY` is an intermediate checkpoint, not a terminal state.** The skill defines the agent-side return value `CONCEPT_READY` to mean: the executing agent has created or reused both task files (`planning/task-concepts/<task_id>-concept-plan.md` and `.opencode/tasks/task-<task_id>.compact.md`), both have matching `Task-ID` headers, both are at their canonical paths, and the correlated original result reports their actual paths, statuses and a short summary. `CONCEPT_READY` is **not** sufficient to advance the Board.
2. **Explicit ordered post-`CONCEPT_READY` sequence.** The orchestrator must complete, in order:
   1. Read the correlated original result and verify each role, `Task-ID` and actual path against the canonical defaults.
   2. If verification fails or paths/IDs are wrong/missing, stop with Board still `todo`; do not silently resend.
   3. With discovered `register_task_document`, bind the verified existing `compact_context` and `concept_plan` files (and any `concept_detail` paths if a plan was split).
   4. Read `get_task_documents` back and require both main roles present, `state:available`, correct paths and revisions.
   5. Only then call the discovered Board move tool to change the task to `in_progress`.
   6. Read the exact Board task back and confirm `in_progress` (and a stable `updated_at`/status field if provided by the connector).
   Each step has an explicit success/uncertain/failure branch; the Board never advances on an uncertain outcome.
3. **Fail-closed semantics on any genuine error.** If file creation failed, an expected path belongs to another task, a registration returned an error, `get_task_documents` does not show both roles as `available`, the Board move tool returned an uncertain/failed response, or the Board readback does not show `in_progress`, the orchestrator stops with the Board task still `todo`. The orchestrator reports the precise last successful step and the precise failure; it does not retry silently and does not recreate files that already succeeded.
4. **Recovery from orphan matching files is explicit and supported.** When a `task_id` already has matching files at the canonical paths (deterministic check, or revealed by an authorized `get_task_documents` after a fresh chat), the orchestrator reuses them: it does **not** ask the executing agent to recreate, it does **not** rename them, and it does **not** fall back to legacy artifact links. After matching `Task-ID` verification, the orchestrator proceeds to the same registration → readback → Board move → Board readback sequence. A path owned by a different `Task-ID` is a collision and stops the run with a path-decision request; it is never overwritten.
5. **Vocabulary is shared across SKILL.md, references and regression rows.** The skill uses the same labels everywhere — `CONCEPT_READY`, `REGISTERED` (both roles bound and read back as `available`), `BOARD_MOVED` (Board move call returned and readback confirmed). A row in `references/regression-scenarios.md` exercises each label transition.
6. **Regression tests reflect actual flow.** A new synthetic test (or method) in `tests/chatgpt_skill_test.py` walks the ordered sequence against a tiny in-memory model of the agent + connector and asserts the transition guard:
   - Agent returns `CONCEPT_READY` with both files at canonical paths → orchestrator must **not** move the Board yet.
   - One of two registrations fails → Board stays `todo`; no second registration call duplicates state; the successful registration is preserved.
   - Both registrations succeed, `get_task_documents` returns both `available` → Board move is invoked and readback confirms `in_progress`.
   - Board move fails or returns uncertain → Board stays `todo`; the orchestrator preserves the registrations and does not recreate files on retry.
   - A previous, orphaned-but-matching pair of files is detected at canonical paths → orchestrator reuses them, does not recreate, and follows the same sequence.
   - An expected path is owned by another task → orchestrator stops and reports the collision; no overwrite, no rename, no Board move.
   The existing text-marker assertions stay green.
7. **No new background process, polling loop, daemon or scheduler is added.** The orchestrator remains a client-side instruction package. The change is documentation + one new `references/initialization-follow-through.md`, edits in `SKILL.md`, `references/board-workflow.md`, `references/task-concept-plan.md`, `references/regression-scenarios.md`, `references/task-compact-context.md`, `bundle.json`, `CHANGELOG.md`, the rebuild artifacts (zip, sha256, latest.json), and one new test method in `tests/chatgpt_skill_test.py` that walks the sequence against a small fake.
8. **Skill package integrity.** New `references/initialization-follow-through.md` is added to `bundle.json` `files`; the `SKILL.md` release marker becomes `**2026-09-29-r20**`; `CHANGELOG.md` gains a matching `## 2026-09-29-r20` section; the zip and `latest.json` are rebuilt via `python3 scripts/build-chatgpt-skill.py`; `python3 -B tests/chatgpt_skill_test.py` passes including the row-based regression assertions, the size-policy/staged-prompt assertions and the new flow-level assertions. All previously green assertions remain green.
9. **Skill source files stay inside the bundle.** No executable scripts, daemon, MCP tool, OpenCode core patch, `opencode-vm.sh` change or adapter change is required. The only product files touched are: new `references/initialization-follow-through.md`, edits in `SKILL.md`, `references/board-workflow.md`, `references/task-concept-plan.md`, `references/regression-scenarios.md`, `references/task-compact-context.md`, `bundle.json`, `CHANGELOG.md`, `tests/chatgpt_skill_test.py`, plus the rebuild artifacts.

## Assumptions and constraints

- The orchestrator skill is a client-side instruction package; it cannot itself guarantee atomicity between adapter calls and the Board backend. The "atomic" follow-through in this task is the orchestrator-side discipline of refusing to advance the Board on any uncertain step, not a new transactionality on the server side.
- The existing adapter contract exposes the registration and readback tools (`register_task_document`, `get_task_documents`, `read_task_document`) and a Board move tool, but they are not in one server-side transaction; the orchestrator must therefore enforce the ordering locally. This is already the wording in `references/board-workflow.md` §"Ordered transition and recovery".
- `CONCEPT_READY` is a skill-level vocabulary term, not a server field. It describes the agent's correlated original result on a successful file creation/reconciliation. The orchestrator never invents it from a prompt receipt alone.
- The two real failures (`task_954ff35f-5228-5fb1-8390-cb4bf210e083`, `task_4ae1d182-0da2-53c1-97e6-081f66c27246`) are the canonical evidence base for the design. The new reference and regression rows must explicitly cite the failure shape "files exist on disk, Board still `todo`, no semantic registration" so future maintainers do not regress.
- Existing single-sentence wording about the ordered sequence in `SKILL.md:135` and the §"Ordered transition and recovery" subsection in `references/board-workflow.md` is preserved; it is sharpened by the new reference and the new vocabulary, not replaced.
- The change is documentation + test for the orchestrator skill. No tests with side effects (e.g., `mcp_tunnel_test.sh`, `mcp_adapter_test.sh`) need to be re-run for this slice; the only test affected is `tests/chatgpt_skill_test.py`, which is fully synthetic and offline.
- "Recovery from orphan matching files" is read-only at first: a fresh chat that knows the stable `task_id` may call `get_task_documents` to discover existing semantic references, or check the deterministic paths. If the connector has no registration, an authorized "initializer" run can still create them. The order is always: detect → reuse → register → read back → move.
- The new reference (`references/initialization-follow-through.md`) is a normal `references/*.md` document: it lives under `integrations/chatgpt/opencode-session-orchestrator/references/`, gets added to `bundle.json` `files`, and is included in the rebuilt zip, sha256 and `latest.json`.

## Alternatives considered

- **A. Add a new server-side Board/filesystem transaction.** Rejected. The orchestrator skill is a client-side instruction package; the change is local documentation and regression coverage. A new server-side primitive is out of scope and would require adapter/connector work, not a skill revision.
- **B. Treat `CONCEPT_READY` as terminal and skip the registration step in the existing rows.** Rejected by the two real failures: both cases stopped exactly because `CONCEPT_READY` was treated as terminal. Hardening the row text alone (without changing the wording in `SKILL.md` and the references) leaves the same failure shape latent.
- **C. Move the registration step out of the orchestrator's responsibility and into the adapter.** Rejected. The adapter already exposes the registration tools; the orchestrator decides when to call them. Putting the call inside the adapter would hide the ordering from the orchestrator and from the row-based regression test.
- **D. Make the orchestrator always start a fresh `task_id` after a partial failure.** Rejected. Files exist with stable IDs; orphan matching files must be reused, not orphaned in favor of a new task. The board description and the ticket's links reference the stable `task_id`; abandoning it would lose the audit trail.
- **E. Add a new background watcher that polls for Board status.** Rejected by the same skill rule as `task_4ae1d182-0da2-53c1-97e6-081f66c27246`: no background process, no scheduler, no daemon. The orchestrator reads on demand.
- **F. Implement the orphan-files recovery by always overwriting with the executing agent's fresh draft.** Rejected. Overwriting a known-good pair of files is destructive; the orchestrator must verify `Task-ID` and reuse.
- **G. Add a new vocabulary term `BOARD_READY` instead of `BOARD_MOVED`.** Rejected. `BOARD_MOVED` is the natural past-tense verb that matches `REGISTERED` and reads well in the row parser. It also avoids implying the Board is "ready" in some abstract sense.
- **H. Bundle the regression test as a Bash script alongside the Python tests.** Rejected. The existing row-based parser and the new flow-level test both live in `tests/chatgpt_skill_test.py` and share the same fixture helpers. Splitting into a separate Bash file would duplicate the parser and lose the in-memory model.

## Decisions and rationale

- **Decision 2026-09-29**: Introduce labelled checkpoints `CONCEPT_READY` (agent), `REGISTERED` (orchestrator) and `BOARD_MOVED` (orchestrator) as the single shared vocabulary.
  - Rationale: the failure modes are observable exactly because the orchestrator conflated the agent's intermediate checkpoint with terminal success. Naming the labels makes the ordering local and testable; the row parser indexes by them; the new flow-level test can assert on them.
- **Decision 2026-09-29**: The orchestrator must never move the Board before `REGISTERED`, and must never claim `BOARD_MOVED` without a successful readback.
  - Rationale: every observed failure (and the canonical evidence in `task_954ff35f-5228-5fb1-8390-cb4bf210e083` and `task_4ae1d182-0da2-53c1-97e6-081f66c27246`) is precisely a Board moved-or-not-moved state that diverges from the registration state. Closing that gap is the task.
- **Decision 2026-09-29**: The orphan-files recovery path is explicit: detect → verify `Task-ID` → reuse → register → read back → move.
  - Rationale: the two real failures left exactly such orphans. Without an explicit recovery path, a future orchestrator run on the same task would either recreate files (and possibly collide) or invent legacy artifact links. Reusing verified files is the safe, atomic choice.
- **Decision 2026-09-29**: `CONCEPT_READY` requires verified file content (actual `Task-ID` from each file's head block), not just paths.
  - Rationale: a path-only report is unverifiable; the orchestrator cannot distinguish a real file from a hallucinated path. Path-only is an explicit reject path with the corresponding regression row.
- **Decision 2026-09-29**: A path owned by another `Task-ID` is a collision; no overwrite, no rename, no fallback.
  - Rationale: matches the existing wording in `references/board-workflow.md` ("a different `Task-ID` at either path is a collision, not permission to overwrite") and the regression row "Existing files already cover the task". The flow-level test enforces the same.
- **Decision 2026-09-29**: No new background process, polling loop, daemon or scheduler.
  - Rationale: the orchestrator skill stays a client-side instruction package; the change is local to that package. The rule is repeated in the new reference so future maintainers do not regress.
- **Decision 2026-09-29**: Bump revision to `2026-09-29-r20`; rebuild zip, sha256 and `latest.json`.
  - Rationale: existing build/test pipeline enforces revision markers; not bumping would silently violate the test suite. r20 is the next revision after r19 (CHANGELOG convention `2026-09-29-rN`).
- **Decision 2026-09-29**: No change to `opencode-vm.sh`, MCP adapter code, `tests/mcp_*`, `tests/openlive*`, or `tests/provider*`.
  - Rationale: the board scope is the orchestrator skill. Touching product code is out of scope and would create a regression surface unrelated to the change.

## Interfaces and data flow

### Input

- A user-confirmed `todo` -> `in_progress` transition package: stable `task_id`, target Board task, authorized write-capable initialization request.
- The executing agent's correlated original result, which carries the `CONCEPT_READY` label and the verified paths/IDs.
- Discovered connector tools: `register_task_document`, `get_task_documents`, `read_task_document` (read), a Board move tool.
- An optional pre-existing pair of orphan matching files at the canonical paths from a previous interrupted run.

### Flow

1. The orchestrator reads the correlated original result.
2. The orchestrator parses the agent's reply for `CONCEPT_READY`, the verified paths, both `Task-ID`s and a short summary.
3. The orchestrator verifies each file at the canonical path (existence, `Task-ID`, head block); on mismatch it stops with Board `todo`.
4. If the connector exposes `register_task_document`, the orchestrator binds `compact_context` and `concept_plan` to the verified paths.
5. The orchestrator reads `get_task_documents` back; both main roles must be `available` with correct paths and revisions. On partial or failed readback, it stops with Board `todo`.
6. The orchestrator calls the Board move tool to change the task to `in_progress`.
7. The orchestrator reads the Board task back. If the readback does not show `in_progress` or is uncertain, it stops with Board `todo`; the registrations are preserved for a later authorized retry.
8. The orchestrator transitions its own conversational state to `REGISTERED` and then `BOARD_MOVED`.

### Output

- One short summary line per orchestrator-side step (success/uncertain/failure).
- A consolidated "follow-through complete" reply when `BOARD_MOVED` is confirmed, listing the verified files, registrations, revisions and the Board task's current status.
- A precise last-successful-step report when the sequence stops short.

## Risks and boundary conditions

| Risk | Mitigation |
|------|------------|
| `CONCEPT_READY` becomes the next "no-op trust me" label | Add a regression row that rejects a Board advance before `REGISTERED`; the new flow-level test walks six scenarios and asserts the orchestrator's action. |
| Foreign `Task-ID` at canonical path is silently overwritten | Existing rule preserved; explicit regression row; flow-level test asserts no overwrite. |
| One of two registrations fails and the orchestrator duplicates the successful one on retry | Existing row "One document registration succeeds and the second fails" preserved; flow-level test asserts registration call count and preserved success. |
| Board move returns uncertain and the orchestrator retries blindly | Existing row "Both references exist but Board move fails or has an uncertain response" preserved; flow-level test asserts no retry on uncertainty. |
| New flow-level test diverges from row text | Test asserts both the labelled names and the row-parser content; both must agree. |
| Orphan files discovered after a fresh chat cause the orchestrator to recreate them | Explicit recovery path documented and tested; the agent is not asked to recreate when paths are already verified. |
| `bundle.json`/`SKILL.md`/`CHANGELOG.md` revision markers drift | The build script enforces all three; both `archive_bytes` and `--check` fail closed. |
| Future external scheduling adds a new follow-through path | Documented in `references/initialization-follow-through.md` and the r20 changelog: any new step adds a new labelled checkpoint and a new regression row; it does not change the rule that the Board never moves before all preceding steps are `REGISTERED`. |
