## 4. Zielarchitektur und Datenfluss

**Kernprinzip:** ein gemeinsamer **Statuskern** (bestehender `DashboardCollector` + Statusvertrag, erweitert), ein gemeinsamer **UI-Render-Kern** (snapshot→DOM), und **zwei dünne Transportadapter**: (T1) Browser-HTTP `/api/v1/status` (vorhanden), (T2) MCP-App über Host-Bridge (neu). Kein zweites Dashboard, kein Aggregator-Dienst, keine zweite Datenhaltung.

### 4.1 Gemeinsame Datenbasis (Statuskern, erweitert)

`DashboardCollector`/`snapshot()` bleiben die eine Wahrheit. **Erweiterung (additiv, schema_version 2, abwärtskompatibel zu v1):**
- `phase`-Projektion je Task: grobe Arbeitslage, **strikt belegbasiert** (siehe §4.5), niemals simuliert.
- `review`/`results_pending`: zur Prüfung vorliegende Ergebnisse **nur** aus vorhandener Evidenz (z. B. korrelierte terminal abgeschlossene Review-/QC-Session-Turns, Management-Journal, Attention) – sonst `unknown`.
- `runtime` bleibt getrennt: `current_runtime` (Setting) vs. `turns[].runtime` (assistant-belegt). Bestehende Semantik unverändert übernehmen.
- `navigation`/`links`: Browser-Pfad behält Session-/Board-Deeplinks; **MCP-App-Pfad enthält keine lokalen URL-Deeplinks als Navigationsannahme** (aus ChatGPT nicht erreichbar) – dort nur IDs/Text + ehrlicher Hinweis, dass Deep-Links lokal sind.
- Projekt-Scope: Pilot zeigt **genau ein** Projekt (dieses Repo). Die UI-Struktur darf eine Projektliste rendern (wie Referenz), aber der Adapter liefert nur den eigenen Repo-Scope; kein Multi-Repo-Aggregator, keine globale Registry.

**Wo lebt der Collector im MCP-App-Pfad?** Der Adapter ist heute stateless; der Collector muss langlebig sein (5-s-Ticks, Freshness). Entwurf: **ein** langlebiger `DashboardCollector`, gebunden an den bestehenden `OpenCodeGateway`/Server-Lebenszyklus im Adapter-Prozess (analog zu `startActivityCollection()`), erzeugt aus **denselben** Readern wie `dashboard-main.ts`. Damit teilen sich Browser-Dienst und MCP-Adapter denselben Code (nicht zwingend dieselbe Prozessinstanz – zwei Prozesse, ein Vertrag, ein Render-Kern). Alternative „MCP-Tool proxyt P+6" siehe §6 (verworfen).

### 4.2 T1 – Browser-Transport (bestehend, minimal erweitert)

`dashboard-http.ts`/`/api/v1/status` bleibt. Einzige Änderung: liefert das erweiterte schema-v2-Snapshot (additiv). UI wechselt von `app.js`-Polling auf den **gemeinsamen Render-Kern** mit `fetch`-Shim. P+6-Lifecycle, Auth/TLS-Reuse, CSP, Caps, Read-Only-Grenzen unverändert.

### 4.3 T2 – MCP-App-Transport (neu, im bestehenden Adapter)

Drei additive Bausteine in `adapters/mcp/src/tools.ts` (bzw. einer neuen `control-app.ts`, die `createMcpServer` aufruft):
1. **UI-Resource** `ui://repo-live/v1.html` (Version im URI als Cache-Key) via `server.registerResource(...)`, mimeType `text/html;profile=mcp-app`, `_meta.ui.csp` **leer/minimal** (`connectDomains:[]`, `resourceDomains:[]` – die App ruft nur Tools über die Bridge, keine externen Domains), `prefersBorder:false`. HTML = gemeinsame UI (inline, ein self-contained Bundle).
2. **Render-Tool** (z. B. `open_repo_live`) mit `_meta.ui.resourceUri = "ui://repo-live/v1.html"` **und** (optional, deklarativ) `_meta["openai/ui"].entrypoints:[{type:"global"},{type:"thread"}]`; liefert `structuredContent` = aktuelles Snapshot (damit Widget sofort rendert). `readOnlyHint:true`.
3. **Data-Tools** (Decoupled Pattern): `refresh_repo_live` (frisches Snapshot, optional `view:summary|detail`) und `get_repo_live_session` (`{session_id}` → Sessiondetail, neueste Messages/Logs zuerst, bounded Previews). Beide `readOnlyHint`, `openWorldHint:false`, ohne Template-`resourceUri`. Die UI ruft sie über `tools/call` auf der Host-Bridge (statt lokalem `fetch`).

Die App-HTML nutzt genau die Bridge der Referenz (`ui/initialize` → `ui/notifications/initialized` → `tools/call refresh_repo_live`; Detail-on-open via `get_repo_live_session`; `ui/notifications/tool-result` für vom Host geschobene Ergebnisse; 30-s-RPC-Timeout; sichtbare Statuszeile). **Kein** lokales URL-Iframe, **kein** `fetch` zu P+6 aus ChatGPT.

### 4.4 Gemeinsame UI-Komponenten + schmale Variante

Ein Render-Kern (Framework-frei, bestehender Stack: Vanilla-JS/HTML/CSS wie `dashboard/app.js`), der aus einem Snapshot-Objekt die Control-Ansicht baut: Kopfbereich (Projekt, Datenalter/Quellenzustand), Auftrags-/Task-Kopf, **Phase-Rail**, Stats, Task-/Session-Listen mit aufklappbaren Details/Belegen/Verlauf (neueste zuerst), Footer-Hinweis „Boardstatus ≠ Laufstatus, Turnabschluss ≠ Abnahme". **Zwei Host-Shims** (je ~20 Zeilen): `fetchShim` (Browser: `GET /api/v1/status`) vs. `bridgeShim` (MCP-App: `postMessage`-RPC) – beide liefern dasselbe Snapshot-Shape an `render()`. **Responsive/narrow** wie Prototyp/Referenz: einspaltig ≤~740 px, Sidebar→Top-Chips, ≥44px-Touchziele, `light-dark`/`prefers-color-scheme`, kein horizontaler Status-Tabellenscroll. Der Prototyp dient als visuelle Richtung (Panel-/Chip-/Phase-/Tab-Stil), wird aber **ent-simuliert** (keine QC-PASS-Vorschau, keine Beispieldaten als Fakten).

### 4.5 Wahrheitsgemäße Semantik: Phase-/QC-/Integrations-/Install-Modell

Die Prototyp-Phasen (Umsetzung / Prüfung / Main-Integration / Teststand) sind **keine** neuen Live-Wahrheiten. Sie werden **nur** auf vorhandene, getrennte Fakten projiziert und sonst `unknown`:

| Anzeige | Erlaubte Evidenz (vorhandene kanonische Quellen) | Niemals daraus ableiten |
|---|---|---|
| Board-Fachstatus | `taskboard.readDashboardTasks().board_status` | Laufstatus, Abnahme |
| Session-Betrieb | `backend_activity` busy/idle/retry (backend) | Turnabschluss, QC |
| Turn-Abschluss | korrelierter terminaler Assistant (`turns[].state`, `finish`) | Task-Done, Integration, Release |

| „Main-Integration" | Git-/Repository-Fakt (Kandidat in `main`-Historie) bzw. Board-/Journal-Beleg – **keine** Live-Backend-Aussage. Im ersten Read-Pilot als eigene Dimension nur mit Beleg, sonst `unknown` | aus Session busy/idle |
