## 3. Entscheidungskonzept (technische Klärung, Entscheidungen des Operators unverändert)

### 3.1 Fehlerklassifikation (drei Klassen, strikt getrennt)

Klassifikation liest ausschließlich den tatsächlich exponierten Terminalzustand nach abgeschlossenen nativen Retries: letzte Assistant-/ErrorMessage mit `error: APIError` bzw. die RetryPart-Kette (attempt N → Terminal). Keine Inferenz aus busy, leerem Text oder Episodenkontext.

1. **Timeout:** bestätigter Provider-Timeout als Terminalzustand (statusCode/Message gemäß echter Fehlerauskunft; Kalibrierung an echten Fehlertexten der konfigurierten Provider ist JIT-Punkt §6). Ein Timeout belegt keinen providerweiten Ausfall — Provider-Skip ist konservative Routingpolicy, keine Kausalbehauptung.
2. **Provider-Quota/Budget-Erschöpfung:** echter Fehlercode mit Quota-Erschöpfungssemantik (z. B. insufficient_quota-Familie/entsprechende Providersemantik). Rate-Limit ≠ belegte Quota: reine 429/„rate limit"-Antworten ohne Erschöpfungsnachweis triggern nicht automatisch; andere Invalid-Requests triggern nie. **Effektive Provider-/Kontingentidentität** = (Provider-ID, credential-/accountbezogene Kontingentidentität so weit sie aus dem tatsächlichen Fehler und der konfigurierten ID belegbar ist). Gleiche Tuple/Alias-/evident-geteilte-Quota-Fälle werden aus Fehlerbeleg + konfigurierter ID geklärt — ohne Secrets, ohne Raw-Dumps, ohne Quota-Plattform; bleibt die Identität unbekannt, wird kein providerweiter Kausal-/Skip-Claim konstruiert (Skip entfällt, Kandidat wird schlicht nicht erneut versucht).
3. **Eingabelängen-/Kontextfehler:** exakt strukturierter `invalid_request_error`, dessen Message/Response-Body das konkrete Muster `Range of input length should be [1, N]` trägt (exakte Range-Erkennung, versionsbezogene Semantik geprüft). N = gemeldete zulässige Obergrenze. Alle übrigen invalid_request_error sind **kein** automatischer Trigger.

### 3.2 Routing bei Timeout/Quota (Klassen 1/2)

- **Total Fallback (Standard):** aus jedem regulär gewählten Ausgangsprofil — ausdrücklich auch Design/Review — direkt auf das konfigurierte abschließende Fallback-Profil, dann genau eine korrelierte Continue-Fortsetzung (prompt_async mit Alignment-Prompt §3.5) in derselben Session am letzten gesicherten Stand. Keine Zwischenstufe, keine eigenen Retry-Zähler, keine Backoff-/Budget-Schicht, native Retries unverändert.
- **Degrading Fallback (wählbare Option):** Ketten mit FINAL-Einstiegspfaden — Deep→Standard→Execution→Fallback; Design→Standard→Execution→Fallback; Review→Deep→Standard→Execution→Fallback. Einstieg beim tatsächlich betroffenen Profil; ein Sonderprofil, das bereits regulär aufgelöst wurde (z. B. Design→Standard), steigt in der verbleibenden Kette ein und wiederholt keine bereits gescheiterten Stufen. Fehlende reguläre Profile und Kandidaten mit bereits gescheiterte effektiver Provider-/Kontingentidentität werden übersprungen; dieselbe Runtime wird nicht retryiert; keine Aufwärtswechsel, keine Schleifen — endliche Routingfolge. Fallback bleibt letzter Versuch.
- **Rollenwahrheit:** technische Profile ändern nie die fachliche Rolle — Designanforderungen bleiben Designanforderungen; der Reviewer bleibt unabhängig, keine Selbstimplementation/-Abnahme.
- **Widersprüchliche gleiche abschließende Fallback-Runtime** (Fallback-Identität == bereits gescheiterte Provider-/Kontingentidentität): Konfigurations-/Prüfthema — bei Aktivierung wird die letzte Kette geprüft; ist das abschließende Fallback auf der bereits gescheiterten Identität konfiguriert, ist das ein Konfigurationsbefund, der als solcher gemeldet wird (§3.4 INPUT_REQUIRED statt Scheinversuch); keine erfundene providerweite Fehlerursache.
- **Per-Step-Rückkehr:** Fallback gilt nur für den konkret fehlgeschlagenen Schritt. Nach dessen Abschluss ermittelt der nächste separat angestoßene Auftrag sein reguläres Profil (Provider/Modell/Denkstufe) frisch aus der aktuellen Projektpolicy, setzt es und prüft es wirksam (Exactreadback, model-switched-Beleg). Kein pauschales Zurücksetzen, keine dauerhafte Profiländerung, kein Zurückschalten während eines laufenden Fallback-Schritts. Scheitert der neue reguläre Versuch erneut an Klasse 1/2, folgt erneut direkt das Fallback; scheitert auch dieses → §3.4.
- **finalFallback unconfigured:** kein automatisches Setzen von Qwen/OpenAI/LM Studio. Vorgesehen ist ein minimaler optionaler Konfigurationsvertrag (§4c). Fehlende/ungeeignete (z. B. zu kleines Kontextfenster) oder erneut gescheiterte letzte Runtime → präzises INPUT_REQUIRED.

### 3.3 Recovery bei Kontextfehler (Klasse 3, separat)

Nach beendeter Anfrage + bestätigtem Klasse-3-Befund: genau eine Compaction der betroffenen Session über die installierte Version (compact/summarize; Modellwahl der Compaction aus aktueller konfigurierter Quelle, nicht aus dem ausgefallenen Profil geraten). Erfolg erfordert belegbar: CompactionPart/nichtleere brauchbare Zusammenfassung **und** passende Folgeeingabe (wirksame Verkürzung; tail_start_id/overflow als Belegflächen). Danach genau eine korrelierte, ausgerichtete Continue-Fortsetzung desselben Arbeitsschritts im **bisherigen regulären Profil samt Denkstufe** — kein unmittelbarer Provider-/Fallback-Wechsel allein aus dem Kontextfehler; gilt für die gerade tatsächlich aktive Runtime (auch eine Fallback-Runtime), kein Rücksprung auf das ursprünglich ausgefallene Profil. Aufgabenidentität, gesicherter Stand, Arbeitsbaum und Ownership bleiben erhalten; keine doppelte Ausführung, keine parallele Compaction/Continue, keine Überlagerung der laufenden manuellen Test-Proxmox-Compaction durch einen zweiten automatischen Vorgang. Kein unmittelbares Resubmit desselben abgelehnten Requests. Compaction- oder erneutes Kontextscheitern → nachvollziehbar dokumentiertes INPUT_REQUIRED, keine unendliche Compaction-/Retry-Schleife, keine zusätzlichen Zähler. Native automatische Compaction vs. adapter-/clientgeroutete Compaction werden abgegrenzt (§6), damit kein doppelter allgemeiner Mechanismus entsteht.

### 3.4 INPUT_REQUIRED-Vertrag (Arbeitszustand, keine erfundene Board-Spalte)

Bei Fallback-/Compaction-/erneutem Scheitern wird der Task dauerhaft dokumentiert: ursprünglicher Fehler (redigierte Klasse + strukturierte Kerndaten), ursprüngliches Profil/Provider/Modell/Denkstufe, eingesetzte Fallback-Runtime, konkreter Fallback-/Compaction-Fehler, korrelierte Nachrichten-/Belegreferenzen, letzter gesicherter Stand und die benötigte Operatorentscheidung. Keine Secrets, keine Rohantworten. Danach keine weitere automatische Fortsetzung.

### 3.5 Alignment-/Recovery-Prompt (verbindlich, statt bloßem Continue)

Jede automatische Wiederaufnahme (nach Runtime-Wechsel **oder** Compaction) erhält einen kurzen expliziten Reinitialisierungsprompt: exakte Task-ID, Paket-/Syntheserevision (falls vorhanden), kanonische Compact-Context-/Concept-Plan-Pfade; zuerst aktuellen C lesen, dann relevante P-Abschnitte und nötige Originalbelege; Auftrag/Entscheidungen/Scope/Sicherheitsgrenzen, tatsächlicher Arbeitsbaum/Owner/Basis/HEAD und vorhandene Receipts/Ergebnisse werden übernommen; Fortsetzung am letzten gesicherten Stand; ungewisse frühere Seiteneffekte werden an Belegen geklärt, nicht blind wiederholt. Keine neue Aufgabe/Session, kein Aufgaben-/Reparaturbudgetreset; C/P laufend aktuell halten; große Plandateien gezielt (Range-)lesen. Kann die letzte Taskdokumentpflege wegen des Ausfalls nicht erfolgt sein, wird der dokumentierte Stand gegen Git/Receipts/Original-Evidence abgeglichen (C/P-Freshness wird nicht unterstellt).
