## Architecture and design

### Responsibility boundaries and one shared engine

**Generic Scheduler Monitor loop** (compact rule in `SKILL.md`; detailed new reference `references/monitor-tasks.md`):

1. Recover the exact master/task-file references, read the full master description/notes and latest effective policy/checkpoint/directive.
2. Apply cheap stop gates before expensive reads: STOPPED/COMPLETE_PASS/PARKED with no newer trusted directive → no-op; then one correlated worker active/busy/pending/uncertain check. No duplicate assignment.
3. Revalidate just-in-time live evidence relevant to the one next permitted action.
4. Choose at most one bounded management action; no parallel mutating action; verify exact receipt/result/state.
5. Append at most one checkpoint after successful action/readback; use readback on uncertainty. No scheduler recursion, self-send, background polling, hidden retry or implicit second task.

**Specialized Monitor policy** belongs in separate references, not duplicated scheduler machinery:

- `references/monitor-tasks.md`: common bootstrap, fixed task primer vs C/P vs notes, lifecycle, directive precedence, common live/read/write/evidence contract, note budget, scheduler concurrency gate and setup receipt.
- New `references/integration-test-monitor.md`: classification, failure fingerprint/progress, bounded harness-repair loop, focused regression, resume-vs-fresh and park/handoff.
- Existing `references/work-packages.md`: add sequential monitored-wave policy and Monitor-specific delta-readiness/integration gates; preserve existing generic package contract and clarify v1 monitor does not activate existing parallel plans.
- `SKILL.md`: short trigger/link/router and hard boundaries only. Do not copy the full recipe into the entry point.
- `references/regression-scenarios.md`: add one row per behavior. Existing test file gets synthetic row/contract assertions and small fakes; no live scheduling in unit suite.

No new MCP schema/tool, VM scheduler, lease store, global ownership registry, per-run Board card or OpenCode supervisor runtime API. Reuse exact task IDs, links, document roles, `get_project_task`, `get_session`/status/progress/activity, result/content reads, `add_task_management_note`, the existing runtime resolver, Board read/write authorization and worktree ownership. Generic work remains normal; only explicit user-authorized monitor setup adds scheduler behavior.

### Master task, stable Description primer, C/P and append-only notes

Exactly one master per monitor. Master task's existing stable **Board Description** holds the immutable/slow-changing primer (update only via normal authorized Board description operation, never via repeated Monitor notes):

- `monitor_schema: v1`, `master_task_id` (must equal this task), pattern (`work_package` or `integration_test`), objective, PASS/stop condition and finite scope/horizon;
- monitored task IDs and recovery rule; for each worker, expected owning session or “not yet assigned”, task/member relation and required integration target;
- allowed management actions, prohibited decisions/mutations, approved harness/test-only write surfaces and acceptance criteria;
- maximum same-fingerprint cycles (default 2), allowed reset/progress evidence and retry/resume/fresh policy;
- required capabilities/connections and no-substitution runtime rules; selected Work supervisor model and OpenCode worker-profile policy stored as separate fields;
- escalation conditions, operator stop procedure, checkpoint size/budget policy, scheduler requested recurrence/time zone/end and single-flight requirement;
- monitor-specific initial `ACTIVE` intent is **not** proof of successful scheduler activation.

The **Concept Plan** is the detailed canonical requirements, design, decisions/rationale, setup/bootstrap, implementation sequence, regression/pilot strategy and genuine open choices. **Compact Context** is one terse current handoff: current lifecycle/effective decision, last live observation, per-worker current exact IDs/state, action/fingerprint/counter, result/integration/worktree evidence, blocker, scheduler/setup receipt pointer, remaining checkpoint budget and next allowed action. It is not a chronological log or duplicate of the primer/plan.

The only append-only run history is one short tagged `Management Note` per active action/readback, e.g. `MONITOR-CHECKPOINT v1 | run=<run_id> | observed=<time> | state=<lifecycle> | master=<id> | workers=<task/session/user-message IDs> | evidence=<result/assistant IDs + observed states> | action=<one action or none> | fingerprint=<value/none> | cycles=<n> | integration=<base/target or n/a> | next=<one permitted action> | blocker=<...>`. Use concise fixed field ordering; redact no correlation IDs needed for recovery but do not store prompt bodies, secrets or unnecessary result text. Include exact source/result references, not paraphrased PASS proof.

Operator directive block is separately tagged `OPERATOR-DIRECTIVE v1`, names the parked checkpoint/run it supersedes, exact decision/scope, authorized/forbidden actions, timestamp/unique directive ID, and expiry/stop conditions. Tag/order make intent parseable but **do not authenticate the writer**; do not regard an ordinary monitor checkpoint or untyped note as authorization. See the open security decision below.

`get_project_task.description` concatenates older and new note blocks in order. In v1 read and parse bounded complete task output; operator directives are effective only if trusted, explicitly marked, and later than the checkpoint they supersede. Later monitor notes do not cancel a directive unless they record its applied disposition. Multiple directives: latest trusted appended directive governs within the original stable task scope; a narrower/newer instruction can supersede an earlier one. Contradictory, truncated, untyped, unreadable or provenance-ambiguous note state parks. The Board's original task outcome/scope always wins over C/P and notes; user instruction wins over Monitor inference; live original results prove execution, not notes.

**Checkpoint budget:** current adapter limits each description to 32,000 UTF-16 code units and full task output to 40,000 UTF-8 bytes, with no note-tail/compaction/delete API. Before activation, measure current task output and reserve enough for fixed primer plus configured maximum substantive runs, one park/final note and operator directive allowance; use a conservative per-note cap (target ≤1,200 UTF-8 bytes including marker) and verify worst-case notes fit both current description and MCP output budgets. Bound active runs/horizon so the budget is finite. No-op wakeups consume none. If readback shows insufficient reserve, park before starting; during a run stop mutating before the next append could overflow and report the remaining budget using any safe channel. Never rewrite/prune prior notes to make space. Do not set “unbounded forever” as monitorable in v1.

### Exact correlation and evidence model

For every monitored worker store and carry the tuple `(project/connector identity, master_task_id, monitored_task_id, session_id, submitted user message_id, submission receipt/time, result assistant message_id(s), result revision/hash/ranges/read coverage)`. Store setup request/Work task identity and scheduler identity separately. Board task `session_ids` or generic links are pointers, not proof that the linked message ran or passed. If one session has multiple tasks, retain each message link distinctly; never correlate by title/time proximity.

Evidence states remain independent: Board status, session activity, task receipt (`submitted/running/completed/failed/aborted/unknown`), tool progress, pending session-wide input, original result read coverage, implementation, local commit, integration/acceptance, and monitor lifecycle. “Task completed” or tool completed is not PASS. PASS requires: exact submitted ID; complete, stable visible terminal result (regular finish, no error/abort/omission that affects conclusion); required test exit/status/log/assertion evidence; required integration/base/acceptance evidence; explicit configured PASS criteria met. Unknown/incomplete/changed content, lost connection, absent trace or unsupported live state cannot be promoted.

FAIL requires exact correlated terminal evidence that configured criteria failed. BLOCKED requires a concrete unavailable prerequisite/permission/input or incomplete integration. Aborted/timed-out/unconfirmed runs are neither PASS nor confirmed FAIL; preserve exact uncertainty. A fix is “successful” only after diff/worktree/owner and focused regression evidence are read. Resume requires that current session/receipt is the exact original work, no pending question/permission or busy/execution evidence, prior test/harness state supports continuation, and target/base is unchanged or revalidated. Otherwise a Fresh Run is a deliberate controlled new attempt with separate message ID after reconciling the previous attempt as terminal and no duplicate active run; preserve the old evidence and link the new one.

### Lifecycle, wakeup and concurrency safety

- `ACTIVE`: normal monitoring; exact live read and at most one bounded management action per active cycle.
- `PARKED_INPUT_REQUIRED`: dependent autonomous mutations stop; checkpoint states precise decision, completed/changed/tested work, exact evidence, repair count/fingerprint, why no action is allowed, operator question/options and safe resumption point. Worker may be retained in safe state; do not force abort or alter permissions.
- `COMPLETE_PASS`: monitor outcome met with the full evidence gate. Does not silently change worker/master Board status or imply external acceptance beyond criteria.
- `STOPPED`: explicit operator end. Preserve evidence and do not reactivate without a later trusted explicit decision.

First wakeup validates master identity, task documents/descriptor and any setup receipt. If effective state is parked/terminal and no trusted later directive exists, stop immediately: no full session scan, no retry, no note. If directive exists, re-read exact relevant Board tasks, notes, session status, receipt/result, permissions/questions, worktree/base and connection/scheduler state; only then record `ACTIVE` and perform one next action. If a worker is actively running, the monitor does not create a new send, repair or later-wave worker; it may record a verified waiting checkpoint once, then subsequent active worker wakeups may use the cheap running/no-op path without repeated notes, as specified in the integration policy.

**Overlapping wakeups:** no native lock/CAS exists for master tasks or management-note directives. Smallest safe v1 protection is a scheduler/Work facility that can set and read back one in-flight execution per scheduled task (max concurrency 1, no queued duplicate management runs). The gate must verify the exact capability/setting in the current platform; a prompt or note does not lock it. Also reuse the same exact master/context and one project connector/session; backend per-session admission catches some simultaneous sends but is not a task-level lock and not universal across clients. If single-flight cannot be established and verified, do not activate autonomous mutation; use the full bootstrap as a draft/manual one-at-a-time process or leave inactive. No speculative lock service, marker lease in append-only notes, status mutation, or “last writer wins” workaround.

### Retry and failure-fingerprint policy

Fingerprint a reproducible tuple, not a natural-language headline: test/harness identity + exact relevant command/config/environment versions + normalized failure class/code + failing test/assertion or first stable stack/error location + relevant fixture/service identity. Exclude timestamps, random ports, transient IDs and unrelated log text. Store enough sanitized parts to explain equivalence; do not publish secrets. Same/practically same fingerprint when those stable components match and no material environment/test/input change is evidenced.

Default counter counts **autonomous repair cycles** for that fingerprint: one cycle is diagnosis evidence → one bounded in-scope repair action → focused regression result. Read-only diagnosis does not count. Implementation clarification: reserve a cycle on repair admission (uncertain admission reserves until reconciled), release only proven non-admission, and retain attempted fixes even when regression is unavailable; this closes interrupted-cycle loops. A repair's own harness version change or A→B→A error sequence cannot evade the original fingerprint's history. Maximum two cycles without material progress; then park. Focused PASS permits continuation but does not erase history when the full run repeats the same failure. Reset a no-progress episode only with attributable evidence resolving or materially narrowing that original failure under unchanged acceptance, not new timestamps/models or unrelated tests. A genuinely different root cause has its own history under the total run/horizon budget. Transient generation/infrastructure continuation defaults to at most one per unchanged episode after exact terminal/test-state readback, independently of the repair cap.

Diagnose before retry when cause is ambiguous, error is repeatable, failure class does not prove a transient provider/generation timeout, a worker result is incomplete, or a full rerun would overwrite useful test state. Immediate park/escalate on out-of-plan product/architecture/schema/security/trust/acceptance decisions, unsafe write target/ownership, production/irreversible action, permission/question, unexplained conflicting writer, scheduler/runtime/connection unable to verify, fingerprint limit, evidence budget exhaustion or ambiguity that changes risk. Explicit bounded retry of a confirmed transient infrastructure error may be one new same-session submission only after exact old receipt/result readback establishes terminal/non-delivery and idle/no-pending state; obey the fingerprint cycle/horizon. `SUBMISSION_UNCERTAIN` is never “retryable” absent exact evidence reconciliation.

## Two v1 monitor patterns

### A. Work Package: strictly sequential Waves

Use the package task as master. Keep stable existing member task IDs; no member-per-action Board cards. In the primer/plan capture members, exclusions, dependency order, wave boundaries, required integration target and acceptance.

For an active Wave, inspect exact member Board task/session/message/result and current worker owner/worktree when mutating. If running, do not dispatch the next wave or a parallel package-preparation/monitor worker. On terminal member result, read the complete original output, classify state, verify actual source HEAD/dirty status/worktree and integration/acceptance state. A Board `done`, `in_progress`, idle session or local commit is not enough. If integration belongs to this wave, one integrator reconciles target tree/diff/base and runs combined required checks; verify actual target HEAD and required content. Record evidence in C/one note, not a duplicate chronological plan.

Only after Wave N is terminal **and** all required integration/result/acceptance/base evidence is verified, perform just-in-time delta readiness for Wave N+1: relevant member/task docs/revisions changed? dependencies satisfied at exact integrated HEAD? decision/input clear? owner/worktree and actual tool target still valid? shared surfaces/resources changed? target/acceptance still same? Reuse existing valid facts, revalidate only deltas. Issue current `WORK_PACKAGE_READY` for the named next wave only, then one next member action. No parallel dispatch because tasks look independent. An unready later wave is parked without undoing or retroactively blocking a prior already-running wave. Local commit, integration, Board task state and external acceptance stay separate.

### B. Long Integration/System Test: controlled diagnose/repair loop

Three logical objects only: technical Integration-Test Task/session (may already run); Monitoring/Master task; one recurring Scheduler Auftrag invoking the management task. No engineering/run task per attempt. Configure criteria/harness/test command and allowed test-only files/resources before activation. Worker is conservative/fail-fast: it reports real failing evidence and never changes acceptance semantics.

On each active cycle:

1. Reconcile exact current run/receipt first. Running/busy -> no new prompt. Pending permission/question -> park/route to first-party operator UI; never auto-answer. Lost connection/incomplete search/result -> no action needing that missing fact.
2. For terminal result, read full original result and classify `PASS`, `FAIL`, `BLOCKED`, `ABORTED/UNKNOWN`. PASS completes only on configured assertions and any required integration/acceptance evidence. A short timeout or tool `completed` marker alone is not PASS/FAIL.
3. For FAIL/BLOCKED, compare exact failure to the plan and fingerprint history. Unknown cause -> bounded targeted diagnosis with suitable *available and verified* worker profile; use `deep` only where policy resolves it, with current exact runtime and permission rules. Diagnosis is not permission to change code.
4. If diagnosis proves the cause is inside explicitly allowed harness/test-environment surface, one manager action may request a narrow reversible fix in the verified worktree/owner. Capture base/HEAD/dirty diff and affected files; no product, schema, security, trust or acceptance edits. Otherwise park with precise `INPUT_REQUIRED` and morning options.
5. After fix, run focused regression first and read exact command/result. If it fails same fingerprint, update counter; after two no-progress repair cycles park. If it passes, choose **Resume** only when exact original session/run is terminal, resumable, idle/no pending input, state/base preserved and no double-submit risk. Else reconcile terminal status, preserve old run and explicitly start a controlled **Fresh Run** as the one next action. Never restart from unknown delivery.
6. Append a compact checkpoint only after the actual action and readback. Park/final checkpoint includes lifecycle, why, last run/receipt and actual result, diagnosis/edits/focused tests, fingerprint/cycles/progress, unresolved decision, safe recovery point and exact next allowed action.

Morning Handoff reconstructs from master + latest trusted directive/checkpoint + live exact task/session/result/worktree evidence. It reports observed-vs-unknown, which fixes and tests actually happened, current state, count/limit, integration/acceptance, operator decision needed, and one safe next action. Operator may append a later trusted decision; next Wakeup performs full live revalidation before `ACTIVE`. No proactive morning notification is promised.

## Interfaces/data flow

`Scheduler wake` → read exact master + ordered tagged notes → resolve effective lifecycle/directive → cheap no-op/worker gate → live Board/session/permission/progress/result + C/P/Worktree evidence → choose one action under generic safety rules + selected specialized policy → exact call/receipt or park → exact readback/original result → at most one appended checkpoint → response/next wake.

Scheduler configuration belongs to external Work platform; no new API surface presumed. Board/task tools remain project-local. Task docs are existing `compact_context`/`concept_plan` bindings. Worker messages use the chosen exact `session_id` and `submitted_message_id`; receipts/results/link evidence retain IDs. A new session/member cannot be silently substituted. Connections are capabilities/selected project, not a skill-pinned alias. No secret, prompt body or hidden reasoning is written to notes.

## Alternatives considered

- **New generic scheduler engine in OpenCode VM:** rejected/out of scope; user wants client-side skill design and uses externally available verified scheduler.
- **Separate scheduler mechanism per pattern:** rejected; same master read/live revalidate/single action/readback/checkpoint loop is technically sufficient; only policy differs.
- **Parallel v1 package waves:** rejected by Addendum 1 due to member/result/base/owner/integration races and unnecessary concurrency complexity.
- **New Board schema, custom per-run task or persistent MCP lock service:** rejected absent evidence; reuse current task IDs, links, notes and exact result APIs. Where existing contracts cannot prove serialization, block activation rather than pretend a marker note is a lock.
- **Automatic note compaction/description rewrite or latest-note MCP endpoint:** not used in v1; no existing API supports safe prune/CAS, and adding it exceeds minimal scope. Finite preflighted run/checkpoint budget + cheap no-op + stop-before-overflow. A dedicated read-tail endpoint can be later evidence-driven work.
- **Retry full integration test after every failure:** rejected; diagnose first, bounded harness-only correction, focused regression then evidence-driven resume/fresh.
- **Scheduler self-disable or manual scheduler edit as correctness:** self-disable optional; correctness relies on lifecycle no-op. User can manually disable.
- **Text marker as cryptographic operator authentication:** insufficient. Requires an explicit trust decision/credible external actor provenance, or fails closed for automatic reopen.

## Decisions and rationale

- **2026-10-01 — v1 has one shared Monitor loop and two specialized policy references.** It minimizes duplicated dispatch, evidence and admission policy while separating genuinely different work decisions.
- **2026-10-01 — Active action versus cheap no-op wakeup.** A no-op on a parked/terminal master must not deep-read, send, or append another note; thus “one checkpoint per run” applies to substantive active management cycles, not every scheduler tick.
- **2026-10-01 — Sequential Waves for monitored packages.** Later Board Addendum 1 resolves earlier general package parallel model for this v1.
- **2026-10-01 — Integration test uses exactly three logical objects and max two no-progress same-fingerprint repairs.** Addendum 2 resolves open lifecycle/loop threshold; no per-attempt engineering task.
- **2026-10-01 — No note-based lock.** Existing task note CAS and cross-client ownership are explicitly absent. Require live scheduler single-flight configuration/readback; otherwise leave automation inactive.
- **2026-10-01 — Human author provenance is not currently present in MCP task readback.** Do not claim an operator-only policy is technically verified from a textual marker. This remains an explicit security decision/gate.
- **2026-10-01 — No fixed cadence/model ID.** These depend on current platform/product/workspace availability and one concrete monitor's duration; discover and obtain confirmation at setup.
